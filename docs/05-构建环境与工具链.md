## 1. 必须做的一步：装 VS Build Tools

在**管理员** PowerShell 或 CMD 里执行（普通权限会弹 UAC，等人工点确认）：

```powershell
winget install --id Microsoft.VisualStudio.2022.BuildTools --exact `
  --override "--quiet --wait --norestart --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
```

或用图形安装器勾选 **「使用 C++ 的桌面开发」** 工作负载（含 MSVC v143 生成工具 + Windows 10/11 SDK）。

装完**重开终端**，验证：

```bash
rustc --version          # 应仍是 1.98.1
cargo build              # 在 apps/desktop/src-tauri 下，应能编过
```

**为什么必须是它**：rustup 的默认 host 是 `x86_64-pc-windows-msvc`，这个目标需要 MSVC 的 `link.exe` 与 Windows SDK 的导入库。而 Tauri 在 Windows 上**官方支持的就是 MSVC**——M4 的分发打包（NSIS / 更新签名）也在同一条链路上。

**路径提示**：装完后项目可以留在含中文的目录（MSVC 用宽字符 API，容忍非 ASCII 路径；反倒是 GNU 的 `ld` 不容忍，见 §3.2）。

## 2. 已修：rustup toolchain 是半成品

**症状**：`rustc` 报

```
error: Missing manifest in toolchain 'stable-x86_64-pc-windows-msvc'
```

而 `cargo 1.97.1` 却能跑。

**根因**：toolchain 目录存在，但 `bin/` 里**只有 `cargo.exe`，没有 `rustc.exe`**，也没有 manifest——是一次中途失败的安装在磁盘上留下的半成品（不是"没装"，所以不能简单当作未安装处理）。

**修法**（已执行）：

```bash
rustup toolchain uninstall stable
rustup toolchain install stable --profile minimal -c rustfmt
```

**结果**：`rustc 1.98.1` + `cargo 1.98.1`，`rustup toolchain list` 正常。

## 3. 试过并否掉的替代路线（别再走一遍）

### 3.1 用 Electron 绕开 Rust

`00` §3 已经把 Electron 否掉过一次（体积 120~200MB；本项目不需要 Node 运行时，其唯一优势消失）。现在多了一条理由：**为了绕开一次 20 分钟的安装而背上一个 150MB 的运行时，不划算**。

### 3.2 用 GNU 工具链（`stable-x86_64-pc-windows-gnu`）绕开 MSVC

看起来很有希望：这个工具链**是自包含的**——自带 `rust-lld.exe` 与 mingw 运行库，不需要 MSVC 也不需要 Windows SDK。实测 hello world 能编译、链接、运行。

**但在本项目上它连不过去，卡在两个独立的问题上：**

**问题 A：非 ASCII 路径让 `ld` 写不出文件**

```
ld: cannot open output file D:\project\项目\笔记sikll\pc软件\...\build_script_build-*.exe: No such file or directory
```

不是权限、不是磁盘（编译到 `/tmp` 就成功，因为那是 ASCII 路径）。

**绕过**：把构建产物导到 ASCII 路径即可，源码路径不用动：

```bash
CARGO_TARGET_DIR="D:/cargo-build/course-reader" cargo build
```

已验证有效：加上它之后，编译从"第 19 个 crate 就失败"推进到"编过几百个 crate"。

**问题 B：`dlltool` 找不到 —— 这条无解，是放弃 GNU 路线的真正原因**

`windows-sys` / `parking_lot_core` 用 `raw-dylib` 链接，GNU 目标下需要 `dlltool`：

```
error calling dlltool 'dlltool.exe': program not found
```

**诡异之处**：`dlltool.exe` **就在工具链里**（`lib/rustlib/x86_64-pc-windows-gnu/bin/self-contained/dlltool.exe`，GNU Binutils 2.44），单独运行完全正常（不是缺 DLL）。但 rustc 按名字找不到它，而以下两种办法**都实测无效**：

| 试过的办法 | 结果 |
|---|---|
| 把 `self-contained/` 加进 `PATH` | ❌ 仍报 program not found |
| 把 `dlltool.exe` 复制到 `lib/rustlib/x86_64-pc-windows-gnu/bin/` | ❌ 仍报 program not found（`sysroot` 已确认、文件已确认在位） |

也就是说 rustc 对 gnu 目标的 `dlltool` 查找既不按 PATH、也不按目标 `bin/`。剩下的路子只有：装真正的 binutils，或换 nightly 用 `-Zdlltool=<path>` 指定。**两者都比装一次 MSVC 更糟**（前者是又一份工具链要维护，后者让产品构建依赖 nightly）。

> 结论：**GNU 路线已被实测否掉**，不要再尝试。已安装的 gnu 工具链保留着，作为"万一 MSVC 装不上"的最后备选，但需要先解决上面两个问题。

## 4. 两个与工具链无关但要知道的坑

### 4.1 Git Bash 里的 `link` 不是链接器

`/usr/bin/link` 是 coreutils 的建硬链接工具，而 Git Bash 的 `/usr/bin` 在 PATH 里排在 MSVC 前面。在缺 MSVC 的情况下，rustc 调 `link.exe` 会被它抢先匹配，报出**与真实原因完全无关**的错误：

```
link: extra operand '...rcgu.o'
Try 'link --help' for more information.
```

`extra operand` 与 `Try 'link --help'` 就是 coreutils 的报错格式——**看到这个错误，真正的问题一定是"MSVC 链接器不在 PATH 上"**，而不是 Rust 代码有问题。装好 VS Build Tools 后这个错误自然消失。

### 4.2 Git Bash 会把 `/xxx` 形式的环境变量值改成 Windows 路径

实测：

```bash
VITE_BASE=/test/ pnpm build          # ✗ 产物里变成 src="/Program Files/Git/test/assets/..."
MSYS_NO_PATHCONV=1 VITE_BASE=/test/ pnpm build   # ✓ 产物里是 src="/test/assets/..."
```

MSYS 的路径转换把以 `/` 开头的**环境变量值**当成 POSIX 路径改写了。所有以 `/` 开头的环境变量都受影响（`VITE_BASE`、各种 `*_URL` 前缀配置等）。

**影响面**：GitHub Actions 跑在 Linux 上，不受影响；只有**本机 Windows + Git Bash 手工构建**时会踩到。要在本机验证 GitHub Pages 那份构建（`base=/<repo>/`）时必须加 `MSYS_NO_PATHCONV=1`。

### 4.3 Node 的 fetch 不读 `HTTPS_PROXY`

同一台机器上 `curl` 能拿到 jsDelivr、Node 却报 `ECONNREFUSED` —— 因为 curl 读代理环境变量，而 **Node 的 fetch（undici）默认不读**。加 `NODE_USE_ENV_PROXY=1` 即可（在脚本内设置 `process.env.NODE_USE_ENV_PROXY = '1'` 也生效，dispatcher 是每次 fetch 时才创建的）。本仓库的 `scripts/*.mjs` 已在文件头设置。

另外实测（开了代理的情况下）：`api.github.com` 与 `cdn.jsdelivr.net` 可达，**`raw.githubusercontent.com` 不可达（4 秒超时）**——所以内容源的回退链以 jsDelivr 与 api 为主。
