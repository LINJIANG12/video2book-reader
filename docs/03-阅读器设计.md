# 03 · 阅读器设计

> **文档性质**：模块设计。本文定义阅读器的数据模型、接缝、渲染规范与验收标准，**不含实现代码**（TypeScript 类型声明仅作为契约表达，不是实现）。
> **上位依据**：`00-架构总纲.md`。本文不得违反总纲的结构不变量。
> **版本**：v2 · 2026-09-22（**v2 把本文拉回与实现一致**：§4.1 管线图按实际重画、§5.1 语言普查补全并修正 `dos` 映射、§2.1 接口字段对齐代码、§5.2 与 §6.2 与 §7 删掉三处从未实现的投机设计、§1.3 纪律一与纪律四补上实测数据、§9.2 与 §9.3 与 §11.3 按实现改写；未决事项改为指向 `00` §11 总表）
> **本文的地位**：阅读是**主功能**（AI 交互是次要功能），所以这是全项目工程量最大、打磨要求最高的一份设计。

## 0. 定位与边界

### 0.1 三条硬边界

| 边界 | 含义 | 为什么是硬约束 |
|---|---|---|
| **不依赖 Agent 运行时** | 阅读器不知道模型、会话、插件是什么 | 静态网页版要「阉割 AI 与记录」后功能完整 |
| **不依赖任何端口实现** | 阅读器只接受一个 `ContentSource` 与一组事件回调 | 三种形态（PC / 静态 / 安卓）共用同一份阅读代码 |
| **不落盘任何东西** | 进度、书签、收藏由调用方决定存哪；阅读器只发事件 | 静态版要「无记录」，若阅读器自己写 localStorage 就阉割不干净 |

**验收方式**：`apps/reader-web` 与 `packages/reader` 的源码中，import 不得落入**禁止清单**（拦的是依赖方向：`plugins/`、`packages/agent`、壳、`node:*`，本地脚本 `pnpm verify:boundaries`，见 `01` §8）；构建产物中不得出现会话、模型、划词相关的**运行时符号与关键词**（不扫类型名——TS 类型编译后已被擦除）。

### 0.1.1 阅读器对外的完整接口（三个 props + 一组事件）

阅读器**不实现插槽系统**——插槽注册表住在 `packages/app`，由它把插件组件装配成下面这几个普通 React props（`01` §2.3）：

```ts
type ReaderSlotProps = {
  selectionActionsSlot?: ReactNode   // 划词动作条的宿主容器（组件自己管可见性）
  toolbarSlot?: ReactNode
  sidePanel?: ReactNode              // 右侧栏（AI 次要 ⇒ 默认收起，由 app 层控制）
}
```

配合固定的三个输入：`contentSource`（读内容）、`readingEvents`（发状态，§9.3）、`readerApiRef`（暴露导航原语，§9.4）。**这就是全部**——阅读器不知道容器里是什么、不知道有 AI、不知道有插件。

（注意：`03` §8.1 的三栏布局里「右：对话栏」是**由 app 层通过 `sidePanel` 放进去的**，不是阅读器自己实现的功能。）

### 0.2 阅读器负责什么

书架、整册渲染（正文 / 公式 / 代码 / 学习要素标注 / 表格）、章级 TOC 与 scroll-spy、册内全文搜索、章级进度、章级书签、**暴露导航原语**（块锚点、章节路径查询、滚动到块，见 §9.4）。

### 0.3 阅读器不负责什么

AI 提问、会话、模型配置、插件、文件系统、网络策略、密钥。全部由调用方通过 `ContentSource` 与事件回调接入。

**其中也包括「划词引用」（`QuoteRef`）。** 它是纯为了喂给模型的产物——在没有 AI 的场合没有任何意义。所以它属于**学习插件**，不属于阅读器：阅读器只给导航原语，插件用浏览器原生 Selection API 加这些原语自己组装引用（§9.4）。这样静态版的产物里**一行划词与 AI 的代码都没有**。

## 1. 内容模型

### 1.1 层级（已在真实文件核实，非推测）

```
课程（16 门）
└─ 册 = textbooks/模块XX_<册名>_精读全书.md        158 册，7~22 万字节
   ├─ H1  册标题 + 元信息引用块
   │      > **所属课程** / **本册内容** / **覆盖范围** / **分册说明** / **整编说明**
   ├─ H2  导读与全景目录（有序列表，列出本册各章）
   ├─ H2  章 ← 这一级就是「一篇模块长文」，原文逐字保留
   │   │   > 对应块：BLK01 | 覆盖分集：P01上 | 块标题（分集名）：《…》
   │   ├─ H3  节
   │   └─ H4  小节
   └─ H2  本册小结
```

另有 `notes/笔记XX_<主题>_笔记.md`（115 篇，6~13 万字节）与部分课程的 `subtitles/`（741 份）。

### 1.2 核实到的结构事实（这些决定解析器怎么写）

| 事实 | 实测值 | 影响 |
|---|---|---|
| 册总数 | **158** | 书架数据量 |
| 册文件大小 | **17,886 ~ 283,156 字节**（最大是 `pink老师-AI前端入门/textbooks/模块08_…`） | 性能基准必须按 size 排序取最大者，**不能写死某一册**（2026-09 实测） |
| 每册 H2 段数 | 中位 **8**（含导读与小结），最多 28 | 一册典型约 6 个正文章 |
| 正文章大小 | 1462 个 H2 段：中位 **10,585 字节**、p90 31,470、p99 53,075、最大 **75,800** | 折算 token 见 `04` §2.3 |
| 导读节 | **158/158 册都有**，但标题有两种：56 册 `导读与全景目录`，102 册 `模块导读与全景目录` | **不能按标题匹配来识别导读**（详见下行） |
| 小结节 | 56 册 `本册小结`；102 册 `模块 NN 全景总结与技术沉淀`（NN 是册序号，长尾不可穷举） | 同上 |
| 章头引用块 | **两套格式**：<br>晚期 56 册 `> 对应块：BLK01 \| 覆盖分集：P01-P07 \| 块标题（分集名）：《…》`<br>早期 102 册 `> 对应分集：P12 \| 原始标题：《12-SQL概述与SQL分类》`（**无 `对应块`、无区间、多一个 `原始标题`**） | 章元信息解析必须分支处理；② 全册骨架的字段集因此**不统一**（见 `04` §2.1） |
| 章间过渡 | `> **承前启后**：上一节讲完「…」，下一节接着讲「…」`（164 处） | 作为一个学习要素标签渲染（§4.2） |
| 笔记的「知识拓扑树」 | 不是 mermaid、不是纯缩进：是 **`*` 嵌套列表（4 空格缩进）+ 内部嵌 `> **定义**：` 引用块** | 必须支持「嵌套列表 × 引用块」的组合渲染 |
| 逐字稿 | 741 份，**全部是 `.txt`**（不是 Markdown） | 不是 Markdown 文档，`DocumentSummary.kind` 要单独取值（见 §2.1） |

### 1.3 ⚠️ 两条实现纪律（实现时踩出来的，别改回去）

**纪律一：标题识别必须交给 Markdown 解析器，不能用正则扫行。**

最初用 `/^## /` 扫行找标题，把**代码围栏内**长得像标题的行也当成了真标题。实测三个案例全由此而来：

| 文件 | 围栏内的"假标题" | 后果 |
|---|---|---|
| `pink老师-AI前端入门/模块02` | 4 行 `## 二级标题（核心业务模块，对应 h2）`——那一章是**教 Markdown 语法**的 | 章数 14 → **11**（其中 1 章是纪律三那处围栏泄漏，真章 10 个） |
| `黑马程序员-Python-AI/模块09` | 6 行 `##     购物车系统     ##`——那是**程序输出菜单的示意图** | 章数 17 → **11** |
| `北京大学-变态心理学/模块06` | 3 行 | 章数 6 → 3（修正后为 **6**，见纪律二） |

改用 `remark` 解析后按**解析器给出的位置**切分，这三处就都对了。**remark 不会犯这个错，我却差点犯了。**

> 表里的"实际"数字以 `scripts/check-render.mjs` 的断言为准——那三册都带回归护栏，规则一变就会被抓到。纪律一的数字与纪律三的泄漏章数**必须一起读**：`pink老师 模块02` 的 11 章里有 1 章是内容缺陷泄漏出来的。

**纪律二：「导读列出的章数」不是权威，内容才是。**

曾按导读条目数截断章数，被 `北京大学-变态心理学/模块06` 证伪：它**正文有 6 章**，而**导读只列了 3 条**——导读是残缺的。所以：

- 切分用**结构派生**：H2 序列排除首部导读与末位小结，**以正文为准**
- 导读条目数只作**诊断提示**（不一致时不阻断渲染，只记一条观察项）
- 用「导读列出的每一条能否在正文里找到对应章」做**对齐校验**——这才是章序号错位的哨兵

**全库校验工具**：`node scripts/check-split.mjs`（扫 158 册 + 115 篇笔记）。当前结果：

```
【册】158 份，共 1137 章   导读条目无对应章: 0   导读缺失: 0   首章 meta 缺失: 0
【笔记】115 份，共 1040 章
通过：无告警，章序号与导读逐条对齐。
```

剩余 3 条观察项都是**内容侧滞后**（`pink老师 模块02` 与 `变态心理学 模块06` 的导读写得比正文少，`pink老师 模块02` 无小结节），按纪律二以正文为准，不影响功能。

**纪律三：`remark` 是标题识别的权威，它遵循 CommonMark——包括 CommonMark 不支持嵌套围栏这件事。**

实测发现一处**内容侧缺陷**（158 册中 1 处，`pink老师-AI前端入门/模块02`）：

```
2702  ```markdown          ← 外层围栏开
2705  ## 1. 表单系统三层架构   ← 作者以为是代码示例里的内容
2716  ```html               ← 内层围栏开
2723  ```                  ← 按 CommonMark，这行关掉的是【外层】围栏
2735  ## 3. 本地化资源配置规约  ← 于是它泄漏成了真标题
```

`markdown` 示例里嵌了 `html` 示例，而 **CommonMark 不支持嵌套围栏**，所以外层的 markdown 块被提前关闭，示例里的 `##` 泄漏成了真标题。用 remark 核实过：`## 3. 本地化资源配置规约` **不在任何 code 节点内**，所以它按标准就是真标题。

**阅读器维持 CommonMark（与 GitHub / VS Code 一致），不用启发式去猜作者意图。** 理由：同一批内容里还有另一种坏法——`变态心理学 模块06` 的围栏若按"宽松解释"，会把 3 个真章节整段吞成代码块；两种坏法方向相反，**没有任何一种阅读器侧规则能同时修好两者**。

**正确的修法在生成侧**：外层代码示例用更长的围栏（四反引号 ` ```` `），CommonMark 就会正确嵌套。已作为已知内容缺陷记录在 `scripts/check-render.mjs` 的用例里（带 `knownLeakedChapter` 断言，规则一变就会被抓到）。

**纪律四：公式定界符写错会吞掉上千行——必须有护栏。**

实测发现第二处内容缺陷，**影响面比嵌套围栏大一个数量级**：

```
1367  $$\frac{25.5}{34}\approx \dots = 25.16
1368  eq 25.5$$        ← 收尾 $$ 写在了行尾
```

按 micromark 的数学扩展，**展示公式的收尾 `$$` 必须出现在行首**。1368 行的 `$$` 在行尾，所以不构成收尾——那块公式一路开到下一处行首 `$$`（3094 行），**吞掉 1728 行、6 个章标题**。这一处的全库影响：章数从 1137 掉到 1109，**28 条导读条目找不到对应章**。

**全库实测范围**（`pnpm check:split` 的观察项，2026-09 重新量过一次）：

| 量 | 值 |
|---|---|
| 含公式失控的文档 | **13 份** |
| 失控处数合计 | **15 处** |
| 跨课程 | **7 门**：Stanford CS336(6)、Stanford CS231N(4)、MySQL(1)、南京大学操作系统(1)、王爽汇编(1)、西电微机原理(1)、黑马 AI 大模型 NLP(1) |

**注意它不只发生在数学课**：操作系统、汇编、微机原理这些课也有。原因是流水线把展示公式的收尾 `$$` 写在了行尾，与课程内容是否"数学"无关。

**护栏（`packages/reader/src/markdown/math-guard.ts`）**：数学节点满足任一条即判为解析失控——

| 判据 | 阈值 | 理由 |
|---|---|---|
| 展示公式跨行数 | > 12 行 | 正常展示公式极少超过几行 |
| 行内公式长度 | > 300 字符 | 正常的行内公式不会这么长 |
| 公式内容里出现标题行 | `^#{1,6} ` | 标题被吞进去是失控的铁证 |

**处理方式是「把那块区域重新解析」，而不是简单换成一段文字。** 这一点很关键：标题在解析阶段就已经被吞进 math 节点了，**事后改文本救不回来**；只有重解析才能把章标题恢复成标题。重解析前先把区域内的 `$$` 转义（`\$\$`），否则同一个坏定界符会再次吞掉后续内容；区域内的**行内公式 `$…$` 保持原样**，它们本来就是好的。

实测效果：章数恢复 1137、导读失配归零，且原文里的行内公式仍然正常渲染。

**与嵌套围栏那次为何处置不同**：嵌套围栏的两种坏法方向相反（一处泄漏、一处吞章），阅读器侧无解，只能在生成侧修；而公式失控是**单向**的（只有"本该是文本却被当公式"，不存在"本该是公式却被当文本"），所以护栏是净收益。

**两处都已在生成侧记为待修内容缺陷，且都是根治点**：嵌套围栏用更长的外层围栏（四反引号）；公式把收尾 `$$` 写在行首。**阅读器侧的两道护栏只是兜底，不是修法。**

### 1.4 术语（避免同一个词指两级）

| 词 | 含义 | 在本文档里写作 |
|---|---|---|
| **册** | 一个 `模块XX_<册名>_精读全书.md` 文件，含若干章 | 册 / document |
| **章** | 册内的 H2，**就是流水线里的一篇「模块长文」**，对应一个块（BLK） | 章 / chapter |
| **节 / 小节** | 章内的 H3 / H4 | 节 / 小节 |

⚠️ **「模块」这个词在仓库里出现两次**：文件名前缀 `模块XX` 指的是**册**，而「模块长文」指的是**章**。写代码与写提示词时一律用本表的「册 / 章」，不用「模块」。

### 1.5 显示单位与对话单位（分离）

| | 单位 | 理由 |
|---|---|---|
| **显示** | **整册，连续滚动不分页** | 仓库 README 明说「模块顺序与课程讲授顺序一致，读起来是连贯的教材而不是拼凑的笔记」 |
| **对话注入** | **单章** | 章就是「一篇模块长文」，中位约 3.3k、最大约 24k token，整套进上下文毫无压力（实测折算见 `04` §2.3） |

这个分离是本设计的核心：**用户感知到在读一整册，而每次请求的上下文成本只有一章。**

## 2. 内容源接缝

### 2.1 接口

```ts
type ContentSource = {
  listCourses(): Promise<CourseSummary[]>
  loadCourse(id: CourseId): Promise<CourseDetail>
  loadDocument(id: DocumentId, signal?: AbortSignal): Promise<string>  // 原始 Markdown
}

type CourseSummary = {
  id: CourseId                  // 目录名
  title: string                 // 课程仓根 README 给的展示名；解析失败回退目录名
  volumeCount: number           // 册数（从文件树派生）
  noteCount: number             // 笔记数（从文件树派生）
  subtitleCount: number         // 逐字稿数（只计数，不列出——v1 无阅读视图）
  direction?: string            // 方向，best-effort 抽取，可缺
}

type CourseDetail = CourseSummary & {
  documents: DocumentSummary[]
}

type DocumentSummary = {
  id: DocumentId                // 仓库内相对路径
  kind: 'volume' | 'note' | 'subtitle'
  title: string                 // 从文件名派生
  originIndex: number           // 从 `模块(\d+)` / `笔记(\d+)` 提取，用于排序
  size: number                  // 字节数：缓存键、性能基准取最大者、「需要联网」判定都用它
}
```

字段来源纪律（**硬纪律**）：

| 字段 | 来源 | 是否可靠 |
|---|---|---|
| `id` / `kind` / `title` / `originIndex` / `size` | 文件树 + 文件名正则 | **确定**，从不解析正文 |
| `volumeCount` / `noteCount` / `subtitleCount` | 文件树计数 | **确定** |
| `title` / `direction`（`CourseSummary`） | 课程仓根 README 的收录表格 | **best-effort**，解析失败只退化为目录名与空方向 |

**v1 刻意不放进 `DocumentSummary` 的两个字段**（都曾出现在设计里，实现时删掉了）：

| 字段 | 为什么不做 |
|---|---|
| `chapterCount` | 必须解析正文才能得到，与「先拉结构、不解析正文」和「首屏 ≤ 2 秒」直接冲突。**进度分母用册不用章**，所以首屏根本不需要它（§3） |
| `summary` | 早期 102 册没有可抽取的一句话主旨来源，晚期 56 册也不全；一个"可缺且只影响卡片上一行字"的字段不值得在类型里占位 |

**`kind: 'subtitle'` 的特殊性**：逐字稿是 `.txt` 不是 Markdown，**没有对应的阅读视图**。v1 只收录**计数**（不构造 `DocumentSummary`、不列文件名），v2 接"原话核对"时再展开（`00` §11 D2）。它也不计入册数 / 笔记数计数。

`CourseSummary` / `DocumentSummary` **全部由文件树派生**（`03` §2.3 的派生原则）——只有 `direction` 是 best-effort，可以缺。

阅读器只认这个接口。**它不知道内容来自 GitHub、本地目录还是内存。**

### 2.2 两个实现

| 实现 | 形态 | 用途 |
|---|---|---|
| `GitHubSource` | **默认**。结构取自 GitHub 文件树，正文按需取 | PC 版首次启动、静态网页版 |
| `LocalDirSource` | 指向本地目录 | 离线使用、自建内容、开发调试 |

**内容源仓库地址可配置**（默认指向 `LINJIANG12/video2book-courses`），别人若自己跑过 video2book，换成自己的仓库即可。

### 2.3 `GitHubSource` 的取数设计

**结构**：`GET /repos/<owner>/<repo>/git/trees/main?recursive=1` —— 一次请求拿到全部文件路径与大小，用于派生课程列表、册列表、笔记列表。

**两种取数模式（部署时决定，同一个实现）**：

| 形态 | 结构**优先**从哪来 | 理由 |
|---|---|---|
| **Cloudflare Pages** | **构建期 manifest**，运行时完全不碰 `api.github.com` | 那些域名在国内经常不可达或极慢，运行时依赖它们会让书架出不来。新课程靠**每日定时重建**跟进 |
| **GitHub Pages** | **运行时取树**（永远最新） | 访客能访问 GitHub，就也基本能访问 `api.github.com` |
| **PC 桌面** | **运行时取树** | 桌面版不能要求"新增课程必须重新发版" |

**关键：两种模式都做兜底，且兜底方向相反。** 优先项失败时自动换另一条路，**永远不会因为一次结构请求失败就整个书架不可用**。

这条兜底不是理论需求——部署当天实测撞上过 `api.github.com` **瞬时 403**（未认证限流 60 次/小时/IP 的窗口边界，或代理抖动），当时页面直接停在"书架还没出来"。对要分发给别人的渠道来说，**这个失败模式太脆**：一个共享出口 IP 的学校/办公室网络就可能触发。所以 GitHub Pages 那份现在也把 manifest 打进产物，只是**排在使用顺序的第二位**。

因此 `GitHubSource` 的签名是 `prefer: 'manifest' | 'runtime'`，两种模式的差别**只是顺序**，代码与产物结构完全相同（都由 `pnpm gen:manifest` 生成 manifest，都在部署工作流里跑）。

**错误信息要能自助排查**：结构读取失败时把两条路的原因都列出来，403/429 额外标注"很可能是未认证限流（60 次/小时/IP）"——用户才知道该等一会儿还是换网络。

**正文**：按需取单册，回退链为 **jsDelivr → api contents → raw**。实测（开了代理）：`cdn.jsdelivr.net` 与 `api.github.com` 可达，**`raw.githubusercontent.com` 不可达**——所以回退链的顺序是照实测排的。

**缓存**：单册拉取后写入本地缓存（PC 走 `FsPort`，静态版走 IndexedDB）。**已缓存的册离线可读**；缓存靠"期望字节数"判失效，而期望字节数本来就在文件树/manifest 里，不需要额外版本号。

**元信息派生原则（硬纪律）**：结构信息（课程名、册名、册数、笔记数、文件大小）**全部从文件树派生**——确定性、不解析正文、不会因正文改版而崩。展示性文案（方向、简介）从课程 README 做 best-effort 抽取，**抽取失败只影响卡片上的一行字，不影响任何功能**。课程顺序优先解析根 README 收录表格得到策展顺序，解析失败回退字母序。

### 2.4 失败与降级

| 情况 | 行为 |
|---|---|
| 无网络且无缓存 | 空状态 + 「重试」与「改用手动指定目录」入口；**不显示错误码** |
| 无网络但有缓存 | 正常读已缓存册；未缓存册标注「需要联网」 |
| GitHub API 限流（未认证 60 次/小时） | 用缓存；提示稍后自动重试；**不阻塞阅读** |
| 单册拉取失败 | 该册显示重试入口；其余册不受影响 |
| 上游结构变化（新增 / 改名课程） | 结构每次启动刷新，自动跟上；缓存键 = 文件路径 + 大小，改名即视为新文件 |

### 2.5 首次启动体验（面向分发的用户，不是作者）

1. 打开即可见书架——**先拉结构（几 KB，秒级）**，不要求任何配置
2. 点开任意一册 → 按需拉正文 → 同时写缓存
3. **AI 入口可见但安静**（右栏默认收起、划词动作条**恒常两项**「复制引用」+「AI 讲解」——注意这两者由 app 层与学习插件装配，阅读器本身不产生 AI 概念，见 `01` §2.3）；未配置模型时点进去是**可行动的配置引导**，不是灰按钮也不是错误页。不主动弹窗、不做启动向导、不发问卷
4. 没有账号、没有登录、没有引导问卷、**没有遥测**

## 3. 书架

- **课程卡片**：课程名、方向（best-effort）、册数、笔记数、阅读进度、收藏星标
- **排序**：策展顺序（根 README 表格）→ 收藏置顶 → 最近阅读
- **进度分母**：用**册**而不是章——「已读册 / 全课程总册数」。理由：总册数从文件树直接可得，而总章数必须下载并解析全部册（最重的课 25 册约数 MB），与 §2.3 的「先拉结构、不解析正文」和「首屏 ≤ 2 秒」直接冲突。
  - 展开到某一册时，改显示「已读章 / 本册章数」，此时该册正文已在内存，分母是已知的
  - **笔记（`kind:'note'`）计入册数分母，逐字稿（`kind:'subtitle'`）不计**——逐字稿没有阅读视图，计进去会让分母永远无法填满
- **「继续读」**：跳回最近一册的最近章
- **空状态**：是行动邀请（「还没有内容，检查网络后重试」），不是错误页
- **逐字稿（741 份）不进主书架**：它是「核对讲师原话」的附属资源。入口放在册详情与册内搜索结果里；v1 只显示条目与文件名（不提供阅读视图），v2 再接渲染

## 4. 渲染管线

### 4.1 管线

**这是实际管线的形状**（`packages/reader/src/markdown/`）：

```
Markdown 源
  → remark-parse          解析（mdast）
  → remark-gfm            表格 / 任务列表 / 脚注 / 删除线
  → remark-math           行内 $…$ 与块级 $$…$$（**解析器扩展，在 parse 阶段生效**）
  ───────────────────────────────────────────────  以上一次性完成，结果被整册复用
  （按「部件」切分：册首 / 导读 / 正文章 / 小结，见 §1.4 与 `model/split-document.ts`）
  → mdast-util-to-hast     取某个部件的顶层节点区间转 hast
  → rehype-katex           公式渲染
  → rehype-callouts        【自研】把 > **标签**：… 识别为结构化学习要素
  → rehype-block-anchors   【自研】给每个块级节点生成确定性 id + 产出大纲
  → hast-util-to-jsx-runtime → React 组件树
```

三处与"直觉写法"不同，都改过，别改回去：

| 项 | 为什么 |
|---|---|
| **两个自研插件在 rehype 阶段，不在 remark 阶段** | 此时引用块已经变成稳定的 `<blockquote><p><strong>` 形状，不用给 mdast 做类型扩展，也少一层自定义节点（`callouts.ts` 文件头） |
| **没有 `remark-rehype`** | 它是 `mdast-util-to-hast` 的 unified 包装层，而这里要按部件的节点区间分别转（各部件块 id 前缀不同），直接调 `toHast()` 更直白。该依赖已于 v2 移除 |
| **Shiki 不在管线里** | 代码高亮跑在 **React 层**（`ui/components.tsx` 的 `CodeBlock`），靠 `IntersectionObserver` 进入视口才触发。全量 Shiki 会让长文档首屏明显卡（§10.2）。管线因此保持**同步、可预测**，也才能在 Node 里直接跑断言（`scripts/check-render.mjs`） |

公式护栏 `guardRunawayMath` 是个**例外**：它是**直接调用的函数**，不是 unified 插件——因为 `unified().parse()` 只跑解析器、不跑 transformer 链，写成插件不会被调用（`remark-math` 能在 parse 阶段生效，是因为它注册的是 micromark 解析器扩展）。见 §1.3 纪律四。

两个自研插件不可省略：`rehype-callouts` 支撑学习要素标注（§4.2，阅读体验最大增量），`rehype-block-anchors` 支撑滚动定位与 §9.4 的导航原语。**注意块锚点不是为划词准备的**——TOC 跳转、搜索命中跳转、书签、进度恢复都用它；学习插件只是复用同一批原语来实现划词引用。

### 4.2 学习要素标注：全表（实测标签，非设想）

以下是对全库 `> **标签**：` 形式引用块的完整统计（按出现次数降序）。这套标签是流水线**已经产出的语义资产**，阅读器的价值之一就是把它显形。

| 分类 | 标签（出现次数） | 渲染 |
|---|---|---|
| **定义** | 定义(795) | 定义卡：左侧竖线 + 「定义」胶囊标签 |
| **结论** | 结论(1401)、核心结论(14)、核心机制(14)、核心原则(11)、核心规则(5)、核心原理(5)、一句话主旨(9) | 结论卡：强调色竖线 + 标签 |
| **提示** | 提示(1291) | 提示卡：中性色 + 信息图标 |
| **易错点** | 易错点(1025)、注意(253) | 警示卡：警示色（唯一允许的第二个语义色）+ 警示图标 |
| **结构过渡** | 承前启后(164)、模块跨度(102)、内容定位(102)、关联说明(102) | 过渡条：低饱和、居中、可含前后章节链接 |
| **册/章元信息** | 所属课程(158)、本册内容(56)、覆盖范围(56)、分册说明(56)、整编说明(56) | 元信息表：册首**弱化展示**（小字号、低饱和），不折叠、不占正文视觉重量 |
| **图示** | 读图说明(87)、图示说明(15) | 说明卡：**锚定到相邻的块**（上一块或下一块）。**不"跟随图片块"**——全库仅 2 处图片引用且都是坏引用（§7），若按图片锚定，这 102 处说明卡将无处依附 |
| **题目** | 题目(36)、题干(24)、解析(18)、答案(8)、需求描述(9) | 题目卡：题干与解析**默认折叠**，点击展开 |
| **其它** | 说明(37)、规则(10)、规范(6) | 通用引用块（不特殊化，避免样式爆炸） |

**设计纪律**：

1. **标签表可配置**（数据驱动，不是代码里的 switch）。出现新标签时退化为通用引用块，**不报警、不报错、不影响渲染**。
2. **不引入超过一个警示色**。分类只区分**九类**（定义 / 结论 / 提示 / 易错点 / 结构过渡 / 元信息 / 图示 / 题目 / 通用），**色相不超过 4 个**。
3. **正文内唯一允许的默认折叠内容是「题干 + 解析 + 答案」**——它把「读」变成「先自测再读」，是学习效果的一部分。册首元信息不折叠（弱化展示，见上表）。
4. 标签的加粗标记被移除（`**易错点**` → 胶囊标签），避免既显示标签又显示加粗造成重复。

**两条踩出来的教训**：

1. **`dos` / `cmd` 映射到 `batch`，不是 `asm`。** 内容里的 ```dos 是 DOS 批处理脚本，与汇编毫无关系；映射到 `asm` 会让批处理代码按汇编语法着色（实测踩过）。这里容易想当然，因为 `dos` 也出现在汇编课里——但那是**语言标签写成 dos 的批处理示例**。
2. **`js` 必须显式别名到 `javascript`。** 否则 `LANG_MODULES` 里虽有 `javascript`，`js` 仍落到"未收录"分支按纯文本渲染。这是**普查不完整**造成的：早期版本的这张表漏了 `js`，于是实现也就漏了别名。

**只收录内容里真实出现的语言**（`ui/components.tsx` 的 `LANG_MODULES`）：`asm` / `bash` / `batch` / `c` / `css` / `html` / `ini` / `javascript` / `json` / `python` / `sql`，共 11 种——上表里每一个映射目标都在这 11 种之内。

**`powershell`(7) 与 `markdown`(8) 暂不收录**：两者 Shiki 都有语法，但合计 15 个块；为这么少的块加两个语言包不划算。**未收录的语言退化为纯文本，不报错**——这是数据驱动表的设计前提（§4.2 纪律 1）。真读到那几册觉得碍眼时再加一行。

> **一个曾经的统计错误，留在这里免得再犯**：早期版本的这张表写「无语言围栏 9614 处，占比很高」。那是用 `grep '^```'` 数出来的，而**闭合围栏本身就是裸的 ```**——9614 里几乎全是闭合围栏。按开/闭状态机重数后，真正的无语言开围栏只有 **4 个**。这个错误直接导致了 §5.2 那条"可选启发式探测"的设计：**它在解一个不存在的问题**。

### 5.2 无语言围栏

**先说事实：这个问题几乎不存在。** 全库 10,764 个代码块里，**只有 4 个**没有语言标记（§5.1）——内容作者把语言标得很齐，而占比最大的 `text`(4372) 是**显式声明"这段按纯文本"**，不是"忘了标"。

v1 策略因此只有一条：

> **按纯文本渲染**（保留等宽与换行），**不猜语言**。

**为什么不做启发式探测**（曾经写进设计、现已删除）：它要付出"探测规则 + 置信度阈值 + 一个可点击切回纯文本的 UI 状态"这一整套东西，而它要解决的问题**只有 4 个块**。更糟的是这条设计来自一个**统计错误**——早期把闭合围栏数成了无语言开围栏（§5.1 末尾的说明），于是凭空造出了一个"占比很高"的问题，再为它设计解决方案。

**真正的修法在生成侧**：缺语言标签时，补标签（内容作者最清楚那是什么），不是让阅读器猜。§5.1 的表说明了同一件事的另一半——**语言标签是内容侧的元数据，阅读器只负责映射已知的与优雅降级未知的。**

### 5.3 懒加载

Shiki 的语法包与主题**按文档实际出现的语言动态加载**，不打进主包。语言映射表本身是静态小数据，放主包。

具体做法（`ui/components.tsx`）：

| 项 | 做法 |
|---|---|
| 引擎 | **JS 正则引擎**（`shiki/engine/javascript`），不用 oniguruma wasm——省掉约 622 KB 的 wasm 与首次加载 |
| 语言 | 逐语言 `import('@shikijs/langs/<lang>')`，用哪个下哪个 |
| 主题 | `github-light` / `github-dark` 双主题，靠 CSS 变量切换（跟随系统） |
| 触发 | `IntersectionObserver` 的 `rootMargin: 600px`——接近视口才高亮，未高亮时按**纯文本**显示（不是空白） |

## 6. 公式（KaTeX）

### 6.1 为什么是必须项

**全库 203 个 .md 文件含行内公式 `$…$`**，多文件含块级 `$$…$$`。课程 README 明确提醒读者：「操作系统、数据库、NLP 与微机原理的模块全书含行内公式，需要在 Typora 勾选**内联公式**，否则公式会原样显示 `$…$` 源码」。**阅读器不解决公式，等于让这四个方向的核心课程不可读。**

### 6.2 已知风险与处置（不是意外，是必须处理的项）

中文技术文档里 `$` 有三种来源：真公式；代码里的 `$`（**天然不受影响**，代码块不参与数学解析）；散文里的 `$`（少见但可能）。处置：

| 措施 | 说明 |
|---|---|
| 只开行内 `$…$` 与块级 `$$…$$`，不开 `\(…\)` 等其它定界符 | 收紧匹配面 |
| 沿用 remark-math 的边界规则（`$` 紧邻数字 / 空格时不匹配） | 规避「花费 $5」这类 |
| **渲染开关**：设置页提供「行内公式」开关（默认开） | 与 Typora 习惯一致，用户可自行关闭 |
| **渲染失败降级**：KaTeX 抛错时原样显示源码，不显示报错红字 | 一个坏公式不该破坏整段阅读 |
| **失控护栏**：见 §1.3 纪律四 | 这才是实测到的真问题（13 册 / 15 处） |

> **曾经的"开发期审计脚本"已删除**（扫描全库 `$…$` 片段、列出"疑似误判"清单、上线前人工过一遍）。它从未被写出来，因为实测表明**真问题是单向的公式失控**——已被 `math-guard` 解决，且验证方式比"人工过一遍清单"强得多（`check:split` 会把每一处失控打印出来）。留一条没人执行、也无人需要执行的设计在这里，只会让下一个人去找一个不存在的脚本。

| 类型 | 实测情况 | 处置 |
|---|---|---|
| **表格** | 大量体系化对比表（本仓库内容的核心表达方式之一） | remark-gfm；横向溢出时容器内滚动，**不撑破页面宽度**；表头吸顶 |

| **mermaid** | 仅 3 个文件 | **v1 不引入渲染器**：按代码块显示（就是现状）。为 3 个文件加一个数百 KB 的渲染器不划算；v2 读到那 3 处真觉得需要时再加（动态 `import()`，不进主包） |
| **脚注** | 少量 | remark-gfm 自带；脚注区放册末，悬停显示内容 |
| 嵌套列表 | 笔记的「知识拓扑树」大量使用（`*` + 4 空格缩进 + 内嵌引用块） | 嵌套列表必须紧凑（缩进逐步减小、行距递减），否则长清单不可读 |

## 8. 排版规范（「简约」落到数值）

### 8.1 版面

| 项 | 值 | 依据 |
|---|---|---|
| 正文行宽 | **38~45 汉字**（大屏居中容器上限约 46 等宽字符宽） | 可读性经验区间；避免中文长行「跳行」 |
| 三栏 | 左：册 TOC（常驻可折叠）｜中：正文（居中固定宽）｜右：**对话栏由 `sidePanel` 插槽提供**（**默认收起**） | 阅读是主功能、AI 次要 |
| 纵深 | 提示卡 / 代码块 / 表格三种块级元素用不同底色深度区分，**不用阴影** | 阴影是「SaaS 卡片感」的来源 |
| 滚动条 | 细、低饱和、悬停才明显 | |

### 8.2 字体与配色

| 项 | 规则 |
|---|---|
| 正文 | 无衬线中文栈（可配置），**不用衬线体**（软件 UI 禁衬线） |
| 代码与公式 | 等宽（代码用带连字的编程字体，公式用 KaTeX 数学字体） |
| 强调色 | **最多一个**，饱和度 < 80%；中性色用 Zinc / Slate |
| 深色 | 跟随系统；**禁用纯黑 `#000000`**，用 off-black（如 Zinc-950） |
| 语义色 | 「易错点 / 注意」允许一个警示色；「结论 / 定义」用强调色的深浅变体，**不新增色相** |
| 中文密排 | 段间距 > 行距；标题**上间距大于下间距**（归属感）；中英文与数字之间自动加空隙 |

### 8.3 动效

只动 `transform` 与 `opacity`。滚动跳转（点 TOC、跳书签）**即时定位，不做平滑滚动动画**——长文档里滚动动画会让人失去位置感。折叠 / 展开用短时程 opacity + transform。

## 9. 导航与阅读状态

### 9.1 块锚点（支撑跳转与定位）

`remark-block-anchor` 给每个块级节点生成**确定性 id**：`章节序号-块序号`（同一份文档每次解析得到同一结果）。

**关键设计：块 id 不是稳定标识。** 文档会随流水线迭代改版，块序号会漂移。因此定下一条**单一规则**（`02` §4 的表结构必须与之一致）：

| 用途 | 存什么 | 漂移后的行为 |
|---|---|---|
| 本次会话内滚动定位 / 划词定位 | `blockId`（`章序号-块序号`） | — |
| 回归上次阅读位置 | `chapterIndex` **必存** + `blockId` **仅作提示** | 提示失效（块不存在或该块已不属于该章）→ **回退到章首**，不报错 |
| 划词引用随消息 | 原文文本 + 章节路径（`blockId` 可存但**只当提示**） | 历史对话永久可读 |

一句话：**块 id 可以存，但只当提示用，任何情况下都不作为"这条记录有效"的依据。** 权威定位一律是 `chapterIndex` + `sectionPath` + 原文文本。

### 9.2 导航

| 功能 | 设计 |
|---|---|
| 章级 TOC | **只收正文章**：册内每个正文章的 H2 作为顶层项、其 H3 作为子项。**册首 / 导读 / 小结不进目录**（否则目录里混进非章节项）；**H4 与小节以下不展开**（避免目录过长）。scroll-spy 高亮当前节 |
| 整册连续滚动 | 不分页、**不虚拟滚动** |
| 上下章 / 上下册 | 按课程知识体系顺序（册序号 + 章序号）；到底 / 到顶时给出可点提示 |
| 册内全文搜索 | **整册已在内存，零索引成本**：直接匹配 + 高亮 + 结果列表跳转（含命中片段上下文）；`Ctrl+F` 原生查找必须仍可用 |
| 跨库检索（16 门课） | **v2**（`00` §11 D3）。PC 版可做真检索；静态版需 Pagefind 类方案，另议 |

### 9.3 阅读状态（阅读器只发事件，不管存哪）

```ts
type ReadingEvents = {
  onChapterEnter?(documentId: DocumentId, chapterIndex: number): void
  onScrollAnchor?(documentId: DocumentId, chapterIndex: number, blockId: string): void
  // onBookmarkToggle 在 M1 未实现（无发射方也无接收方），实现书签 UI 时恢复——见下方说明
}
```

**粒度**：章级书签。**不做摘录本、不做导出、不做段落高亮**（已定案）。

> **`onBookmarkToggle` 的现状（诚实记录）**：本文 §0.2 把"章级书签"列为阅读器职责，但 v1 实现里**没有书签按钮、也没有发过这个事件**——它曾经在类型里声明着，却无发射方、无接收方，是个会让人误以为书签已可用的空接口，已在 M1 实现时删除。
>
> **M1 要把它接回来**，且入口是明确的：书签按钮属于 `toolbarSlot`（§0.1.1 已预留）。按钮由 app 层装配、点击后回调成 `onBookmarkToggle` 上报，阅读器仍不知道"书签"这个概念存在——与划词走 `selectionActionsSlot` 是同一个形状。

**这里没有 `onQuote`。** 划词属于学习插件，不属于阅读器（§0.3）。

### 9.4 对外暴露的导航原语（`ReaderApi`）

阅读器暴露一组**纯导航**原语。每个成员都有一个**非 AI 的消费者**——它们不是为 AI 预留的接口，而是 TOC、搜索、书签、进度本来就需要的能力：

```ts
type ReaderApi = {
  scrollToBlock(blockId: string): void
  // ↑ 消费者：TOC 跳转、搜索命中跳转、书签跳转、恢复上次阅读位置

  getBlockContext(blockId: string): { chapterIndex: number; sectionPath: string[] } | undefined
  // ↑ 消费者：scroll-spy 高亮 TOC、书签命名、进度上报

  getOutline(): OutlineNode[]
  // ↑ 消费者：TOC 面板、册内搜索结果分组

  getPosition(): { chapterIndex: number; blockId: string }
  // ↑ 消费者：阅读进度、scroll-spy
}

type OutlineNode = { title: string; level: 1 | 2 | 3; blockId: string; children: OutlineNode[] }
```

**学习插件怎么用它**：插件自己监听浏览器 `Selection` 事件 → 找到最近的 `[data-block-id]` 容器 → 用 `getBlockContext(blockId)` 拿到章序号与标题路径 → 组装出 `QuoteRef`（`02` §3）。

于是「划词引用」这个概念**只存在于插件里**：静态版不装载学习插件，构建产物里自然就没有任何划词代码。

### 9.5 内容查询面（`ContentQuery`）—— 与导航原语分开

`ReaderApi` 只管**已渲染文档的导航**。插件还需要读**别的**文档（`04` §2.4 的四个工具），这属于内容访问，不是导航，因此单列一个接口，挂在 `PluginContext.content` 上（`01` §2 定义）：

```ts
type ContentQuery = {
  /** 每个方法都带取消通道——「停止」按钮必须在任意阶段有效（04 §5.4） */
  getDocument(id: DocumentId, signal?: AbortSignal): Promise<string>   // 原始 Markdown
  getChapter(id: DocumentId, chapterIndex: number, signal?: AbortSignal): Promise<string>
  listDocuments(courseId: CourseId, signal?: AbortSignal): Promise<DocumentSummary[]>
  searchDocument(id: DocumentId, query: string, signal?: AbortSignal): Promise<SearchHit[]>
  getCourse(id: CourseId, signal?: AbortSignal): Promise<CourseDetail>
}

type SearchHit = { chapterIndex: number; sectionPath: string[]; snippet: string }
```

**它不是为 AI 准备的接口**——非 AI 消费者：册内全文搜索（§9.2）、上下章 / 上下册导航（§9.2）、册详情页的附属清单（§3）、v2 的逐字稿入口。实现是 `ContentSource` + 缓存 + 解析结果缓存之上的一层只读门面。

**与阅读器的关系**：`ContentQuery` 由 `packages/reader` 暴露（它本来就持有 `ContentSource` 与解析缓存），阅读器自身不用它做导航（导航走 `ReaderApi`）。**它不依赖插件、不依赖 agent**——所以静态版同样可以有它，只是没有调用者。

## 10. 性能

### 10.1 规模推算（基于实测文件尺寸）

一册 **17.9 KB ~ 283 KB**（实测 158 册；最大是 `pink老师-AI前端入门/textbooks/模块08_…`，283,156 字节）。

| 量 | 估算 | 结论 |
|---|---|---|
| 渲染后 DOM 节点 | 约 3 千 ~ 1.3 万（按 283 KB 上限推算） | React 单次渲染可接受，**不需要虚拟滚动** |
| 代码块数 / 册 | 几十 ~ 上百 | **全量 Shiki 会明显卡顿，必须懒加载** |

### 10.2 策略

| 策略 | 说明 |
|---|---|
| **不做虚拟滚动** | 它会破坏浏览器原生选中 / 复制、`Ctrl+F`、滚动锚点这三件阅读核心能力。宁可多渲染节点 |
| 代码高亮 `IntersectionObserver` 按需触发 | 接近视口才高亮；未高亮时按纯文本显示（**不是空白**） |
| `content-visibility: auto` | 给章级容器做 CSS 层 containment，加速离屏章的布局与绘制 |
| 解析结果按册缓存 | 切章、切笔记不重新解析 Markdown |
| Shiki 语法按需 import | 见 §5.3 |
| **性能基准** | M1 用**文件树中 `size` 最大的一册**作基准（当前是 283 KB 的 `pink老师-AI前端入门/模块08`，**不写死册名**，随内容更新自动跟上）：首次可交互、滚动、册内搜索耗时都要记录数值 |

## 11. 静态网页版（零安装主分发渠道）

### 11.1 与 PC 版的关系

**同一份 `packages/reader` 代码**，只换装配：

| | PC（Tauri） | 静态网页 |
|---|---|---|
| `ContentSource` | `GitHubSource` 或 `LocalDirSource` | `GitHubSource` |
| 缓存 | `FsPort` 落盘 | `StorePort`（IndexedDB） |
| 进度 / 书签 | 落盘 | **内存实现 → 关掉即无记录**（这就是「阉割记录」） |
| 划词 | 「复制引用」+「AI 讲解」（**恒常两项**，见 `01` §2.3） | **不实现**——浏览器原生的选中与 `Ctrl+C` 已经够了，我们不提供划词扩展 |
| AI | 学习插件 | **完全不存在**（不装载学习插件） |
| 更新 | 自动更新 | **推送即生效，无需任何人重新安装** |

**静态版的定位是「纯阅读站」**：它不装载学习插件，因此产物里没有会话、没有模型、没有划词、没有任何 AI 代码。这不是被裁剪过的版本，而是**同一个阅读器换了一套装配**（`01` §3.1）——两者的阅读体验完全一致。

### 11.2 为什么它是并列主渠道而非附属

「大部分电脑上能跑」这个要求，网页版是**唯一零安装、零门槛、跨设备**的答案：手机、平板、Mac、公司锁死的电脑都能打开。**推送新内容或修 bug 只需一次部署，不需要任何人做任何事。** PC 版提供给需要 AI 交互与离线阅读的人，网页版服务其余所有人。

### 11.3 部署

**两个托管目标，两套策略（已实装，`.github/workflows/deploy-reader.yml`）**：

| | GitHub Pages（`linjiang12.github.io/video2book-reader/`） | Cloudflare Pages |
|---|---|---|
| 结构来源 | **运行时实时取文件树**（永远最新） | **构建期 manifest**，运行时不碰 `api.github.com` |
| 适合 | 能访问 GitHub 的网络 | 国内网络（那些域名经常不可达或极慢） |
| 新内容 | 立刻可见 | 靠**每日定时重建**跟进（最多滞后一天） |
| 兜底 | 产物里也打进 manifest，作为失败时的第二条路 | 同样保留运行时取树作为兜底 |

**两者共用同一份代码**：差别只是 `VITE_CONTENT_PREFER` 的值（`runtime` / `manifest`），而 `GitHubSource` 的两个模式**互为兜底**（§2.3）。所以任何一个渠道都不会因为一次结构请求失败就整个书架不可用。

放在**独立仓库**（`video2book-reader`），**课程仓零改动**——不动它的根目录结构（遵守 `课程/RULES.md` 的策展规矩），内容通过 GitHub API 与 CDN 读取。课程仓根 README 里只加了一行在线阅读入口。

### 11.4 版权与免责

应用内展示内容来源仓库链接与免责声明入口，**不改变原仓库的授权立场**（原文：仅供个人学习复习检索使用，不得用于商业用途，不代表原作者与所属机构观点）。分发形态不构成对该立场的任何涨缩。
