### 0.2 明确的非目标

排除以下方向，避免架构被动膨胀：

- **不做通用 agent**。工具集与提示词由业务插件自带，核心不含任何业务语义。
- **不做第三方插件生态**。插件作者只有一个人——这是后面所有「精简」决策的前提。
- **不做云端模型**。不内置任何模型厂商、不做账号体系、不做额度、不托管密钥。用户自己填一条「自定义模型」。
- **不上 RAG / 向量库**（理由见 §7.3）。
- **不做摘录本、不做学习产出导出**。
- **不做跨端同步**。各形态的会话与进度各自独立，不做云端漫游。
- **不做遥测**。零上报、零账号、零登录、无引导问卷。

## 1. 设计理念：向 dsh 抄什么、不抄什么

dsh（DeepSeek Harness）的架构定义是 *everything is a plugin* —— 一棵 Cordis 插件树，恰好长成了一个 Agent。它的三层分离是：

| 层 | 提供者 | 内容 |
|---|---|---|
| Cordis 运行时 | 元框架 | Context、Fiber（插件生命周期）、Registry、Events（可逆注册） |
| DSH 产品能力 | 官方插件包 | LLM、Session、System Prompt、Tools、Agent Loop、Sandbox / FS / Shell |
| 装配层 | 配置 | Bundle（可复用组合）→ Profile（命名运行时方案）→ Patch（覆盖树，后者胜） |

### 1.1 必须继承的三件事

| 继承项 | 说明 | 对本项目的价值 |
|---|---|---|
| **能力接缝**<br>Service Definition / Provider / Consumer | 三角分离：接口稳定，实现可换，调用方无感 | 换内容来源、换存储、换模型协议时不动业务代码；**也是「一套代码三种形态」成立的前提** |
| **一切皆插件 + 可逆注册** | 工具、视图、提示词、上下文提供者走同一注册入口；卸载即回收 | 这是「可灵活扩展精简」成立的前提，不是加分项 |
| **分层装配** | 基础包 + 场景包 + 用户覆盖 | 换一个 Profile 就换一套 agent 人格与工具集 |

### 1.2 明确不继承的四件事

| 不继承项 | 判断理由 |
|---|---|
| **Cordis 的 Fiber + 依赖注入容器** | 它服务的是「多个团队在同一 runtime 上装配出不同 agent 配置」。本项目单人开发、单人使用，收益远小于心智负担与调试成本。另：cordis 本体当前是 `4.0.0-rc.10`（RC 版本），API 可能微调。**我们只抄它的契约形状**（`manifest` + `setup(ctx)` + 注册即返回注销函数），约 300 行能通读能调试；将来若真要迁 cordis，插件代码不用重写 |
| **`cordis.patch.yml` 覆盖语法** | 单人项目用「对象深合并 + 插件 id 为键」已经足够，不值得发明一门小语言 |
| **独立服务进程 + 跨进程协议** | 见 §2.1。它只在服务「多端共享一个内核」时才必要 |
| **运行时装第三方插件包** | 动态加载、版本兼容、沙箱、签名、加载失败态——这些正是「不稳定」的主要来源。改为构建期打包（`01` §0） |

> **一句话原则**：抄 dsh 的**架构分层与接缝思想**，不抄它的**元框架实现**。目标是「轻量版 dsh」，不是移植 dsh。

### 1.3 一条比抄 dsh 更重要的约束

既然定位是「只为特定任务优化」，那么 **`system prompt`、工具集、视图、循环策略必须全部是插件产物，核心不得硬编码任何业务语义**。

违反这条，「精简」就只是口号——每加一个新任务都得改核心。

## 2. 总体架构

### 2.1 一套代码，三种形态

```
                 ┌──────────────────────────────────────┐
                 │  核心包（纯 TS，环境无关）              │
                 │  reader · agent · plugin · ports(接口) │
                 └───────────────┬──────────────────────┘
                                 │ 只通过「能力端口」访问外界
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
┌───────────────┐      ┌───────────────┐      ┌───────────────┐
│ PC（Tauri 2）  │      │ 静态网页        │      │ 安卓（后续）    │
│ 全功能         │      │ 纯阅读          │      │ 全功能         │
│ fs/net/secret │      │ net 只读       │      │ 各端口原生实现  │
└───────────────┘      └───────────────┘      └───────────────┘
```

**v1 曾把「内核是唯一有状态进程、三端是瘦客户端」当作公理，并由此推出必须造：独立进程 + 跨进程协议 + 双向反向请求 + 内核二进制跨平台分发。这四样全部可以不要。** 逐个核对服务进程到底在提供什么：

| 服务进程的用途 | 还需要吗 | 替代 |
|---|---|---|
| 调模型 | 需要 | HTTP + SSE 流式，**纯 fetch 即可，不需要任何 LLM SDK** |
| 存会话 / 进度 / 书签 | 需要 | IndexedDB（三处行为一致，零原生代码） |
| 执行工具（读另一章、册内检索、抽术语） | 需要 | 阅读器本就持有整册内容，**同一个 JS 上下文里直接算** |
| 读写本地目录 / 密钥 | 需要 | **壳的能力端口**（Tauri `fs` / `stronghold`） |
| 前端与后端共享类型 | 不需要了 | 同一份 TypeScript，直接共享 |
| 崩了不影响 UI / 关窗后继续跑 | 不需要 | AI 是次要功能，没有无人值守任务 |
| 多端同时连一个内核 | 不需要 | 顺序交付；且已定「不做跨端同步」 |

**收益是连锁的**：v1 风险表里最重的三条同时消失——R1（内核二进制跨平台分发）、R3（三端同源的两个接缝必须早期设计对）、R4（安卓无法本地跑内核）。

**为什么这个形状仍然正确**：没有任何单一框架能同时覆盖 PC、网页、安卓（Tauri 覆盖不了浏览器，Capacitor 覆盖不了桌面，Electron 覆盖不了安卓）。所以正确解法不是「选对框架」，而是**让核心逻辑与环境无关**，三种壳各自提供能力端口。这也是 OpenCode / Codex / Zed 收敛到的形状。

### 2.2 分层职责

| 层 | 职责 | 明确不含 |
|---|---|---|
| **核心包** | 阅读器、Agent 运行时、插件注册表、端口**接口** | 任何业务语义、任何 UI 框架、任何原生能力 |
| **插件** | 业务能力（工具、视图、提示词、上下文提供者、模型适配器） | 不直接碰端口实现 |
| **壳** | 端口实现、窗口 / 托盘 / 权限、更新 | 零业务逻辑、零密钥落盘 |
| **接缝** | `Ports`（能力）、`ContentSource`（内容） | — |

### 2.3 参考实现对照

| 机制 | 借鉴来源 | 本项目落地 |
|---|---|---|
| 会话三原语 | Codex（`Item` / `Turn` / `Thread`） | 沿用，但取消 wire 编码（`02` §2） |
| 插件契约形状 | dsh / cordis（`name` / `inject` / `apply` / `Config`） | `manifest` + `setup(ctx)` + 注册返回注销函数（`01` §1） |
| 上下文稳定性优先 | dsh 的前缀缓存工程化纪律 | 提升为可运行时校验的 `stability` 断言（`01` §2.5、`04` §2.2） |
| Profile 决定工具集 | Zed（Ask / Write / Minimal） | Profile 决定插件装配与 agent 人格（`01` §5.1） |
| MCP 的定位 | Codex 试过并否掉 | **不作为主协议**，仅保留为可选扩展通道（v1 不实现） |
| 端口 + 多壳 | Tauri / Capacitor 生态惯例 | 五个端口，三形态实现（`01` §3） |

## 3. 技术选型

| 层 | 选型 | 理由 | 已排除 |
|---|---|---|---|
| 前端框架 | React 19 + TypeScript + Vite | 三形态通吃；组件库生态最厚 | Vue |
| 应用外壳组件库 | **shadcn/ui + Tailwind**（M1 落地，用于书架 / 设置页 / 对话面板 / 表单这类**交互**部件） | 组件源码复制进项目、可改可删；键盘与可访问性行为开箱即用 | Ant Design（重）、Mantine（体积） |
| 正文排版 | **自写 CSS**（`packages/reader/src/styles.css`），**不引入任何 UI 框架** | 阅读器要渲染的是中文文档排版（行宽 38~45 汉字、段间距 > 行距、KaTeX 与代码块共存），没有任何组件库提供这一层；且 shadcn 的默认观感（阴影卡片）与 `03` §8.1「纵深用底色不用阴影」直接冲突。**这条边界同时守住不变量 3**：UI 框架只进 `packages/app` 与 `plugins/`，一个都进不了 `packages/reader` | 让阅读器依赖 UI 框架 |
| Markdown | unified（remark / rehype）+ KaTeX + Shiki | 需要自定义标注与块锚点，通用渲染器撑不起（`03` §4） | react-markdown 裸用、marked |
| 桌面壳 | **Tauri 2** | 5~10 MB、复用系统 WebView2、内存低；Rust 侧插件齐全（fs / stronghold / http / notification / tray）；**请求从 Rust 侧发出，不受 WebView CORS 限制**——这对调你本地的 `127.0.0.1:8045` 是硬需求 | Electron（120~200 MB；本项目**不需要 Node 运行时**，其唯一优势消失） |
| 运行形态 | **无独立服务进程**；Agent 运行时为纯 TS 包 | 见 §2.1 | 独立内核 + 协议层 |
| 存储 | IndexedDB | 三形态一致、零原生代码 | SQLite（三套实现） |
| 密钥 | Tauri `stronghold` | 修正现有配置的明文密钥问题 | 明文 JSON |
| 包管理 | **pnpm + `node-linker=hoisted`** | 多包结构标准选择；hoisted 规避本机 symlink 限制（`三端规划与大方向.md` 有实测记录：无开发者模式 → pnpm 符号链接失败） | 若 hoisted 仍失败则回退 npm workspaces |
| 模型接入 | 三个协议适配器（openai-chat-completions / anthropic-messages / google-native），纯 fetch + SSE | 零 SDK 依赖；覆盖用户能想到的一切端点 | 内置厂商通道、SDK 依赖 |
| 静态站 | Vite 构建 + 独立仓库 + GitHub Pages | 零安装、跨设备主分发渠道 | — |
| 安卓 | Capacitor 提供同一套端口 | 只做桥，不碰业务 | Tauri Android |

**为什么 `github-web/` 在顶层而不是 `apps/` 下**（一处刻意的结构选择）：

`apps/` 下放的是**壳**——它们要接入能力端口、要装业务插件、最终长成一个完整应用。而 GitHub 静态站不是壳：**它是同一份阅读器的另一条分发现场**，零安装、跨设备、推送即生效，也是全项目唯一带自己部署工作流的产物（`.github/workflows/deploy-reader.yml`）。把它与 `desktop` / `mobile` 并列在 `apps/` 下，会让人以为它也要走"端口 + 插件"那套装配，而它恰恰**永远不该装那些东西**（不变量 5）。

**它与其余部分的唯一接触面是 `packages/reader`**（2 个 import：`@app/reader` 与 `@app/reader/styles.css`）。**这份共用是刻意的、不能拆**：静态站与 PC 版共用同一份渲染管线，才使得「PC 版修好了静态版不会漏」成立；若各留一份副本，就必然漂移（本仓库已经栽过同类坑——`gen-manifest.mjs` 曾复制 `derive.ts` 的派生逻辑，靠去重才修掉）。

### 结构不变量（后续改动不得违反）

1. `packages/agent` 不依赖 `plugins/*`
2. `packages/app` 不依赖 `plugins/*`（前端靠运行时契约，不靠编译期引用）
3. **`packages/reader` 不依赖 agent / 插件 / 端口实现 / 任何壳**
4. **删掉整个 `plugins/`，项目仍能构建并启动为一个可对话的空 agent**
5. **删掉 `plugins/` 与 `packages/agent`，`github-web/` 仍能构建并完整可用**，且其产物中**不含划词、`QuoteRef`、模型、会话的任何代码**

第 4 条是「可精简」的验收标准；第 5 条是「静态版阉割 AI 与记录」的验收标准。**第 3 条是最容易被日常开发悄悄破坏的一条**，必须由本地脚本 `pnpm verify:boundaries` 的**依赖方向检查**兜住（不引入 CI，见 `01` §8）。

## 5. 插件系统

完整契约见 **`01-插件与端口契约.md`**。此处只记要点：

- 插件 = **构建期打包的可拆装模块**（workspace 包 + 贡献点 + 配置启停），不是运行时装第三方包

- **按真实消费者增量实现**：没有消费者的贡献点不实现（这是防止机制空转的具体手段）

## 6. 会话模型

完整定义见 **`02-数据模型.md` §2**。此处记要点，并补上 v1/v2 都没写的 **Agent Loop 本身**。

### 6.1 三原语与 wire

- 三原语 `Item` / `Turn` / `Thread` 沿用 Codex 的形状
- **取消 wire 编码**：无跨进程传输，流式是同进程内的 async iterator
- 记录字段（时间戳、状态、错误）**绝不允许进入上下文前缀区**

### 6.2 Agent Loop（v1/v2 缺失，这里定案）

一个 `Turn` 的执行步骤：

| 步 | 动作 |
|---|---|
| 1 | **组装上下文**：按 `order` 调用全部 `context` 贡献点的 `provide`，得到前缀段与消息段；按 `stability` 校验并生成 `segmentFingerprints` |
| 2 | **发起请求**：调 `LlmAdapter.stream`，把 `text` / `reasoning` 事件逐块追加到当前 `AssistantMessageItem`（`status: 'streaming'`），`usage` 事件写入 `Usage` |
| 3 | **工具轮**：若模型产出 `tool-call`，按 `isConcurrencySafe` 决定并行或串行执行，结果作为 `ToolResultItem` 追加到消息序列，**回到第 1 步**（前缀段不变，只增消息段——这是缓存能命中的原因） |
| 4 | **收敛** | 见下 |

**终止条件**（四种，缺一不可）：

| 条件 | `Turn.status` | 说明 |
|---|---|---|
| 模型 `finishReason === 'stop'`（无工具调用） | `completed` | 正常结束 |
| 工具轮数达到上限（默认 **16** 轮） | `failed` | 提示"达到工具调用上限"。**必须有上限**——否则一个反复调工具的小模型能烧掉一整天的额度 |
| `signal.abort()`（用户点停止） | `aborted` | 任意阶段都生效，包括工具执行中与等待首 token 时；已流出的文本保留（`04` §5.4） |
| 任一失败（网络 / HTTP / 超时） | `failed` | 行为表见 `04` §5.4 |

**三条纪律**：

1. **不自动重试**。重发整段前缀是有成本的，静默重试会让成本数字无法解释（`04` §5.4）。
2. **工具轮回到第 1 步时，前缀段必须逐字节不变**——只有消息段增长。这是"同一轮内多轮工具调用仍能命中缓存"的前提。
3. **`AbortSignal` 贯穿四处**：`LlmAdapter.stream`、`ToolContribution.execute`、`ContextContribution.provide`、`ContentQuery` 的取数。

### 6.3 线程绑定：核心不解释业务字段

`Thread` 只认 `scope: { kind, key }` 与不透明的 `binding`（`02` §2.3）。**「一章一会话」是 v1 学习模块的约定，不是核心规则**——它写在 `plugins/study` 里。

这样第二个任务（例如命理排盘）可以用自己的 `scope.kind` 与 `binding` 组织会话，**不需要改核心一行**。这是 §1.3「核心不得硬编码任何业务语义」在会话模型上的落实，也是「后面还会扩展其他任务」这个要求的验收点（`02` §10 第 9 条）。

## 7. 核心机制：文档上下文注入

完整设计见 **`04-学习交互设计.md` §2**。此处只记要点与不可动摇的判断。

### 7.1 显示单位与注入单位分离

| | 单位 | 理由 |
|---|---|---|
| 显示 | **整册**（连续滚动） | 仓库 README：「模块顺序与课程讲授顺序一致，读起来是连贯的教材」 |
| 注入 | **单章**（= 一篇模块长文，中位约 3.3k、最大约 24k token，实测折算见 `04` §2.3） | 用户感知到在读一整册，每次请求只付一章的成本 |

### 7.2 三条硬规则

| 规则 | 说明 |
|---|---|
| **前缀绝对稳定** | 前缀区（系统提示词 + 全册骨架 + 当前章全文）不得含任何易变数据。它是 prompt cache 的命中依据 |
| **划词永远走消息层** | 划词提问作为**新的一条 user 消息**，附带章节路径与原文，而不是回写前缀。回写前缀 = 缓存全废 |
| **确定性序列化** | 前缀区内容由确定性序列化生成，字段顺序固定——顺序抖动同样导致缓存不命中 |

这三条被实现为可运行时校验的 `stability` 断言，并有 `segmentFingerprints` 采集用于实测归因。

### 7.3 明确不上 RAG

| 判断 | 理由 |
|---|---|
| 不做向量库 / 切片检索 | 场景是「精读一份文档」。全文注入在**跨章节推理**上完胜切片检索，且省掉整条 embedding 管道的维护成本 |
| 何时才该上 RAG | 文档量到数百份、上下文确实塞不下时才考虑。届时它是 `context` 贡献点的另一个实现，**架构无需重构** |

> 这条设计的意义：把「要不要 RAG」从架构决策降级为插件替换。

## 9. 路线图

| 里程碑 | 目标 | 验收标准 |
|---|---|---|
| **M0** | 环境 | 修 rustup toolchain、建 workspace、Tauri 壳就位；**`NetPort` 能接到逐字流**（冒烟验证接线——注意此时还没有模型适配器，见下）；在无 WebView2 的环境里安装包能自动补齐。**本机实测缺 C/C++ 工具链，需先装 VS Build Tools，全部细节与已否掉的替代路线见 `05-构建环境与工具链.md`** |
| **M1** | PC 框架 + 阅读器（主功能） | 包结构、端口、插件运行时（**只 `views`/`slots`**，见 `01` §9）、Tauri 壳、书架 + 整册渲染 + 公式 / 代码 / 学习要素标注 + TOC + 进度 + 册内搜索。**在全新环境里完整读完一册**；公式不显示源码；易错点 / 结论一眼可辨；**用文件树中 `size` 最大的那一册**（当前 283 KB）做性能基准；**删掉 `plugins/` 仍能构建启动并完整阅读**；`pnpm verify:boundaries` 通过 |
| **M2** | AI 学习交互 | `plugins/study`：章 / 册会话、划词引用提问、13 项学习技能（9 划词 + 4 章/册）、自定义模型设置页、`context`/`tools`/`prompts`/`providers` 四个贡献点。**前缀稳定性**必过（`segmentFingerprints` 逐轮一致）；**缓存命中**在会报告明细的端点上测得 > 0；未配置模型时阅读零影响 |
| **M3** | 静态阅读站 | 独立仓库 + Pages，课程仓零改动；线上读完 16 门课；**证实它是纯阅读站**——换掉 2 个端口 + 换 `StorePort` 装配后功能完整、无记录残留、产物里无划词与 AI 代码 |
| **M4** | 分发 | GitHub Releases + 自动更新 + `embedBootstrapper`。在**另一台干净的 Windows 10/11 电脑**上下载安装、正常使用、收到更新 |
| **M5** | 安卓 | Capacitor 包**完整应用的 web 代码**（`apps/desktop` 那份，含学习插件），能读能问；端口实现换成 Capacitor 版 |

**依赖关系**（v2 有一处依赖环与一处错指，已修正）：

| 里程碑 | 依赖 | v2 的错误 |
|---|---|---|
| M1 | M0 | — |
| M2 | M1（**`views`/`slots`**，因为 `context`/`tools`/`providers` 本身就在 M2 实现） | v2 写「依赖 M1 的 `context` 与 `providers`」——而这两者按 v2 自己的表也在 M2 实现，构成 M2 依赖 M2 的环 |
| M3 | M1（阅读器，**不依赖 M2**） | — |
| M4 | M1 | — |
| M5 | **M2 + M4**（要完整应用的 web 代码） | v2 写「依赖 M3（同一套 web 代码）」——而 M3 的产物按定义**不含 AI**（零划词、零模型），不可能既"同一套"又"能读能问" |

## 10. 风险与权衡

下表从 R2 起（R1 已排除，见本节末尾）。

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R2** | **公式误判**：中文文档里 `$` 与 bash `${x}`、SQL 变量冲突，KaTeX 可能把非公式当公式（全库 203 个文件含行内公式） | 部分段落渲染异常 | 代码块天然不解析；收紧定界符；提供渲染开关；上线前用审计脚本列出疑似误判清单人工过一遍；渲染失败降级为源码 |
| **R3** | **阅读器脱离 AI 的纪律会松**（最容易发生的架构腐化） | 静态版无法真正阉割 | 结构不变量 3 的依赖方向检查（`pnpm verify:boundaries`，`01` §8）；`github-web/` 构建失败即报警 |
| **R4** | **插件机制空转** | 前期变慢而收益不明 | 双验收（不变量 4/5）；**按真实消费者增量实现贡献点**，没有消费者的不实现 |
| **R5** | **大册**（文件树中 `size` 最大者，当前 283 KB）的渲染与滚动性能 | 阅读体验 | 不做虚拟滚动（会破坏浏览器原生选中 / 复制、`Ctrl+F`、滚动锚点）；代码高亮按需触发；`content-visibility`；M1 用 size 最大的那一册做基准（不写死册名） |
| **R6** | **GitHub API 未认证限流 60 次/小时** | 书架可能拉不到结构 | 结构每次启动只请求一次 + 本地快照；限流时用缓存并提示，**不阻塞阅读**；正文走 CDN 不占 API 配额 |
| **R7** | **上游内容结构变化**（新增课程、改名、排版批次差异） | 解析崩坏 | 结构信息全部从文件树派生；正文解析对缺节 / 缺字段 / 异常层级全面容错（`03` §1.2）；展示文案 best-effort，失败只影响一行字 |
| **R8** | IndexedDB 位于 WebView2 用户数据目录，可能被清理工具清掉 | 丢会话与进度 | 已接受：丢的只是会话与进度（内容缓存可重建），最坏情况是重读，功能不受损。不为此引入 SQLite |
| **R9** | prompt cache 稳定性依赖供应商实现 | 成本预估偏差 | 采集 `segmentFingerprints` 实测归因（`02` §5）；若某供应商缓存不可靠，可在 Provider 层加前缀裁剪策略 |
| **R10** | 单人维护多包 monorepo | 长期维护负担 | 包数量克制（当前 5 个 packages + 2 个 apps + 1 个 plugin）；不引入 CI 复杂度（边界校验用本地脚本，见 `01` §8） |
| **R11** | **章序号（`chapterIndex`）的派生规则脆弱**：全库 158 册有两套导读/小结标题，且同一标题存在不可见字符差异（实测同一字符串分成 90 + 12 两组）。按标题匹配会让 102 册的章序号整体偏移，**且不报错** | 静默污染线程 / 进度 / `read_chapter` / `QuoteRef` | 已定案：**从正文结构派生**（H2 序列排除册首导读与末位小结），标题只用于识别「哪一节是导读/小结」且用**包含**而非等值比较（`03` §1.3 纪律二）；**导读条目数不是权威**——它只作诊断提示（已被 `变态心理学 模块06` 证伪：正文 6 章、导读只列 3 条）。验收工具是 `pnpm check:split`（全库 273 份逐条核对导读与章的对齐，当前 0 失配） |
| **R12** | **端点不报告缓存明细**（本地反代、Ollama、多数中转站），"命中率"不可观测 | 成本面板数字缺失；M2 验收项无法判定 | 已定案：`cachedPrefixTokens = -1` 表示未知，与 0 分开显示；M2 验收拆成"前缀稳定性必过 + 命中率在可观测端点上测"（`04` §6.3） |

## 附录 A · 决策速查

| 决策 | 结论 |
|---|---|
| 抄 dsh 什么 | 能力接缝、一切皆插件 + 可逆注册、分层装配、前缀缓存纪律 |
| 不抄 dsh 什么 | Cordis Fiber / DI 容器、`cordis.patch.yml` 覆盖语法、独立进程 + 协议层、运行时装包 |
| 运行形态 | 一套代码三种形态；**无独立服务进程**；核心包环境无关，靠能力端口访问外界 |
| 前端框架 | React 19 + TS + Vite |
| 组件库的边界 | **应用外壳用 shadcn/ui + Tailwind**（书架 / 设置页 / 对话面板 / 表单）；**正文排版自写 CSS**，任何 UI 框架都不得进 `packages/reader` |
| 桌面壳 | Tauri 2（Windows 10/11） |
| 会话模型 | `Item` / `Turn` / `Thread`，**取消 wire 编码**；核心只认 `scope: {kind,key}` + 不透明 `binding`；**「一章一会话」是 v1 学习模块的约定，不在核心** |
| Agent Loop | 组装上下文 → 流式请求 → 有工具调用就执行并回到组装（前缀段不变）→ 四种终止（正常 / 工具轮上限 16 / 用户中止 / 失败）；**不自动重试** |
| 存储 | IndexedDB（不是 SQLite）；静态版两个 `StorePort` 实例（内容缓存持久化、会话与进度内存） |
| 端口 | 5 个（fs / net / secret / store / notify）；静态版换掉 **2 个**（fs、secret）+ 换 store 装配；`NotifyPort` v1 无消费者、实现推迟 |
| 内容源放哪 | `GitHubSource` / `LocalDirSource` 是**内置模块（`packages/app`）**，不在 `plugins/` 下——否则删掉 plugins 后阅读器没有内容源 |
| 密钥在哪 | Tauri `stronghold`；配置文件与日志里永不出现明文 |
| 内容从哪来 | 默认 GitHub（文件树取结构 + CDN 取正文 + 本地缓存）；本地目录可选 |
| 文档怎么进上下文 | 显示整册、注入单章；前缀绝对稳定；划词走消息层 |
| 要不要 RAG | 不上。等文档量真正撑爆上下文时，作为 `context` 贡献点的新实现替换 |
| 模型接入 | 只做「自定义模型」；三个协议适配器；不内置厂商、不做账号、不托管密钥 |
| 分发与更新 | GitHub Releases + Tauri updater + `embedBootstrapper`；网页版是并列主渠道 |
| 隐私 | 零遥测、零账号、零登录 |
| 「可精简」怎么验收 | 删掉 `plugins/` 仍能构建启动（不变量 4）；删掉 `plugins/` 与 `agent` 后静态版仍完整可用且产物无划词与 AI 代码（不变量 5）；两者由本地脚本 `pnpm verify:boundaries` 检查 |
| 「可扩展」怎么验收 | 新增一个假想的第二插件，能用**自己的** `scope.kind` 与 `binding` 建线程，且不改 `packages/agent` 与 `packages/plugin` 一行（`02` §10 第 9 条） |
