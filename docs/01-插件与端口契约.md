# 01 · 插件与端口契约

> **文档性质**：契约定义。本文是内核与插件之间、核心包与运行环境之间的**唯一契约面**。TypeScript 类型声明在此是契约表达，不是实现。
> **上位依据**：`00-架构总纲.md`。内容查询面 `ContentQuery` 的语义见 `03` §9.5。
> **版本**：v2 · 2026-09-22（v2 补齐了 v1 中"被引用但未定义"的全部类型，并删除了一个泄漏进核心的 `QuoteRef` 依赖）

---

## 0. 先说清「插件」在本项目里的含义

**插件 = 可拆装的模块**：一个 workspace 包 + 贡献点注册 + 配置里可启停。**不是运行时装第三方 npm 包。**

理由（已定案，不再讨论）：本项目**不做第三方插件生态，作者只有一个人**。而运行时装包要付出动态加载、版本兼容、沙箱、签名、加载失败态这一整套代价——那些正是「不稳定」的主要来源。改用一个可客观验收的标准即可：

> **删掉整个 `plugins/` 目录，项目仍能构建并启动。**（结构不变量 4）

构建期打包换来的是：加插件 = 加一个包 + 一行配置；精简 = 删包或改配置；懒加载 = 动态 `import()` 自动分包；**没有加载失败这回事**（编译期就报错）。

## 1. 插件单元

```ts
type Plugin = {
  manifest: PluginManifest
  setup: (ctx: PluginContext) => void | Promise<void>
}

type PluginManifest = {
  id: string                  // 唯一，kebab-case（如 'study'）
  name: string                // 展示名
  version: string
  description: string
  activation: Activation
  contributes: ContributionKind[]   // 声明式：本插件会用到哪些贡献点
}

type ContributionKind = 'views' | 'slots' | 'tools' | 'context' | 'prompts' | 'providers'

type Activation =
  | { kind: 'onStart' }                    // 启动即加载。提供 views 的插件必须用它
  | { kind: 'onView'; viewId: string }      // 用户打开该视图时才加载
  | { kind: 'onDemand' }                    // 首次调用其工具 / 技能时才加载
```

### 1.1 为什么是 manifest + setup 两个部分

| 部分 | 形态 | 收益 |
|---|---|---|
| `manifest` | **纯数据模块，零副作用** | 启动时就能读出「有哪些插件、各提供什么视图」，**而不执行任何插件代码**——这是冷启动速度的基础，也是 `onView` 入口在插件未加载时仍能显示标题与图标的前提 |
| `setup` | 通过动态 `import()` 按 `activation` 加载 | 自动代码分割；重型插件（如完整学习模块）不拖慢冷启动 |

`contributes` 的用途是文档化与开发期校验（**注册了未声明的贡献点只警告、不失败**——稳定性优先于严格性）。

### 1.2 启动顺序（必须明确，否则 `onView` 与首屏会打架）

| 阶段 | 做什么 | 是否阻塞首屏 |
|---|---|---|
| 1 | 读全部 `manifest`（纯数据），构建视图入口列表 | — |
| 2 | 加载并 `await` 所有 `activation: 'onStart'` 插件的 `setup` | **阻塞**（它们的注册要参与首屏） |
| 3 | 渲染视图宿主 | — |
| 4 | 用户打开某视图 / 首次调用工具时，按需加载对应插件并 `await setup` | 不阻塞，视图内显示加载态 |

**规则**：`onStart` 插件的 `setup` **必须被 await 完成后才渲染视图宿主**；`onView`/`onDemand` 插件在加载完成后通过 `Registry.subscribe` 触发宿主重渲染（§2.1）。

## 2. 贡献点

六个。**全部注册入口都返回注销函数**（§4）。

```ts
type PluginContext = {
  views:     Registry<ViewContribution>
  slots:     Registry<SlotContribution>
  tools:     Registry<ToolContribution>
  context:   Registry<ContextContribution>
  prompts:   Registry<PromptContribution>
  providers: Registry<ProviderContribution>

  /** 内容查询面：读别的文档、检索、列文档。实现见 03 §9.5 */
  content: ContentQuery

  ports:  Ports                          // 见 §3
  config: Readonly<Record<string, unknown>>  // 三层合并后的最终值，见 §5
  log:    Logger
}

type Disposer = () => void

type Logger = {
  debug(msg: string, fields?: Record<string, unknown>): void
  info(msg: string, fields?: Record<string, unknown>): void
  warn(msg: string, fields?: Record<string, unknown>): void
  error(msg: string, fields?: Record<string, unknown>): void
}
```

**本文档中引用的、定义在别处的类型**（避免出现"被引用但未定义"）：

| 类型 | 定义位置 |
|---|---|
| `ContentQuery` | `03` §9.5 |
| `ReaderApi` / `CourseSummary` / `CourseDetail` / `DocumentSummary` / `ContentSource` | `03` §2.1、§9.4 |
| `Thread` / `Turn` / `Item` / `MessageAttachment` / `Usage` | `02` §2、§5 |
| `LlmProtocol` | **本文 §2.7（唯一定义处）**，`02` §6 引用它 |
| `StudySkill` / `QuoteRef` | `04` §4.1 / `02` §3 —— **两者都是插件侧类型，核心一律不引用**（附件与能力都走不透明机制，见 `02` §2.1、本文 §2.6） |

### 2.1 `Registry<T>` —— 必须可读、可订阅

```ts
type Registry<T> = {
  register(item: T): Disposer
  list(): readonly T[]
  subscribe(onChange: () => void): Disposer
}
```

**为什么必须有 `list` 与 `subscribe`**：`01` 说过「插槽注册表住在 `packages/app`，由它把插件注册的组件装配成 props 传给阅读器」——装配的前提就是能**枚举**；而 `onView`/`onDemand` 插件可能在首屏之后才注册，宿主必须能在**晚注册时重渲染**。只有 `register` 的注册表在这两件事上都做不了。

### 2.2 `views` —— 顶层视图入口

```ts
type ViewContribution = {
  id: string
  title: string
  icon?: string
  order: number
  /** 懒加载：宿主用 React.lazy 包，未加载时入口仍显示 title/icon（来自 manifest） */
  component: () => Promise<{ default: ComponentType<Record<string, never>> }>
}
```

用途：实现「不同任务有不同入口」。v1 的视图集合：**书架 / 阅读 / 设置**（全部来自内置模块 = `packages/app`）；将来新增任务模块（如命理排盘）就是一个新的 view。

### 2.3 `slots` —— 往既有界面注入组件

```ts
type SlotName =
  | 'reader.selection.actions'      // 划词动作条的宿主容器
  | 'reader.toolbar'
  | 'reader.sidepanel'              // 右侧栏
  | 'bookshelf.card.actions'
  | 'conversation.message.actions'
  | 'conversation.input.dock'
  | 'settings.section'

type SlotPropsMap = {
  'reader.selection.actions': { reader: ReaderApi; content: ContentQuery }
  'reader.toolbar': { reader: ReaderApi }
  'reader.sidepanel': { reader: ReaderApi; content: ContentQuery }
  'bookshelf.card.actions': { course: CourseSummary }
  'conversation.message.actions': { thread: Thread; item: Item }
  'conversation.input.dock': { thread: Thread }
  'settings.section': Record<string, never>
}

type SlotContribution<K extends SlotName = SlotName> = {
  slot: K
  id: string
  order: number
  component: () => Promise<{ default: ComponentType<SlotPropsMap[K]> }>
}
```

**只有一种机制**：插件渲染自己的组件，宿主只提供一个**空容器**。

```ts
// 阅读器接受的 props（普通 React props，不依赖插件系统）
type ReaderSlotProps = {
  selectionActionsSlot?: ReactNode
  toolbarSlot?: ReactNode
  sidePanel?: ReactNode
}
```

阅读器把 `selectionActionsSlot` 渲染成一个空容器，**组件自己管理可见性**（没有选区时渲染 `null`）。这样：

| 守住的不变量 | 怎么守住的 |
|---|---|
| 阅读器不依赖插件系统（不变量 3） | 它只接受 `ReactNode` |
| 阅读器不产生任何划词 / AI 概念 | 它**不知道容器里是什么**，也不知道选区存在 |
| `QuoteRef` 只存在于插件（`02` §3） | 组件自己用浏览器 `Selection` API + `reader.getBlockContext(blockId)` 组装 |

**三个状态，不要混为一谈**：

| 状态 | 划词动作条 | 原因 |
|---|---|---|
| **未装载学习插件**（如静态版） | 容器为空，**什么都不出现** | 阅读器与 app 层不产生任何划词与 AI 概念 |
| **已装载学习插件、但未配置模型** | 「复制引用」+「AI 讲解」（**恒常两项**）；点后者进配置引导 | 入口可见但安静，引导是可行动的（`04` §5.5） |
| **已装载学习插件、已配置模型** | 同上两项；点「AI 讲解」→ 展开右栏并列出技能 | `04` §5.3 的界面状态机 |

**为什么不需要阅读器通知「用户选了一段」**：`Selection` 是浏览器的原生能力，插件自己监听即可。阅读器不必为插件的事件需求开一个口子——只提供它自己也要用的导航原语（`03` §9.4）就够了。

### 2.4 `tools` —— agent 可调用的工具

```ts
type ToolContribution = {
  name: string                  // 全局唯一
  description: string
  parameters: JsonSchema        // 方言见下
  execute: (args: unknown, exec: ToolExec) => Promise<ToolResult>
  isConcurrencySafe?: boolean   // 未声明 = 串行（写操作必须串行）
}

/** JSON Schema 的一个受限子集，避免三家协议映射时出现表达不出的构造 */
type JsonSchema = {
  type: 'object'
  properties: Record<string, {
    type: 'string' | 'number' | 'integer' | 'boolean' | 'array'
    description?: string
    enum?: (string | number)[]
    items?: { type: 'string' | 'number' }
  }>
  required?: string[]
}

type ToolExec = {
  /** 当前线程：插件从这里取"用户在读哪一册"——**册不进工具入参**，模型不该知道 */
  thread: Thread
  turn: Turn
  /** 取消通道：必须贯穿（04 §5.4） */
  signal: AbortSignal
  content: ContentQuery
}

type ToolResult =
  | { kind: 'text'; text: string }
  | { kind: 'error'; message: string }   // 预期内失败
```

三条契约纪律：

| 纪律 | 原因 |
|---|---|
| **预期内失败返回 `kind:'error'`，意外异常才 throw** | 前者是给模型看的（参数错了、找不到该章），模型读到后能自我纠正；后者是 bug，应当上抛（收场规则见 §4.1） |
| **工具名全局唯一，重名在开发期直接报错** | 重名会让模型看到两个同名工具而无法自洽。宁可启动失败，也不要带病运行 |
| **上下文一律经 `exec` 传入，不进工具入参** | `documentId` / `courseId` 由 `exec.thread.binding` 提供（`02` §2.3）；模型不该知道也不该猜这些内部标识 |

v1 的工具全部来自 `plugins/study`：`read_chapter` / `search_document` / `list_documents` / `read_notes`（见 `04` §2.4）。全部在**同一进程内**执行，不需要独立服务进程。

### 2.5 `context` —— 上下文提供者（本项目最关键的贡献点）

```ts
type ContextContribution = {
  id: string
  order: number
  provide: (req: ContextRequest) => ContextSegment[] | Promise<ContextSegment[]>
}

type ContextRequest = {
  thread: Thread
  /** 本轮用户消息的附件（**不透明**）。插件自己按 kind 过滤并解释 */
  attachments: MessageAttachment[]
  signal: AbortSignal
}

type ContextSegment = {
  /** 稳定标识（= 贡献点的 id）。断言按 (id, group) 配对同一段，见下 */
  id: string
  role: 'prefix' | 'message'
  stability: 'global' | 'volume' | 'chapter' | 'turn'
  /**
   * 断言分组键。**由插件提供、核心不解释**。
   * global → 固定 ''；volume → 册的标识；chapter → 册+章的标识；turn → 忽略
   */
  group?: string
  text: string
}
```

**`stability` 是本设计的关键机制**：它把 `04` §2.2 的「前缀区不得含易变数据」从一条文档纪律变成**可校验的断言**：

| `stability` | 断言（核心只做比对，不推导） | `group` 由插件填 |
|---|---|---|
| `global` | 在**所有**请求间逐字节一致 | 固定 `''` |
| `volume` | 在**同一 `group`** 的所有请求间逐字节一致 | 册的标识（v1 学习模块填 `documentId`） |
| `chapter` | 在**同一 `group`** 的请求间逐字节一致，换组后允许变化 | 册 + 章的标识（v1 填 `` `${documentId}#${chapterIndex}` ``） |
| `turn` | 每轮可变（历史、划词引用、本轮任务），不参与断言 | 忽略 |

**为什么需要插件提供 `group`**：核心只认 `Thread.scope: { kind, key }` 与不透明的 `binding`（`02` §2.3），它**无法从 `scope.key` 推导出"两个线程属于同一册"**。而 `volume` 级断言恰恰要求跨线程比对。让插件显式声明分组键，既保住了断言的精确性，又不用让核心去解释业务字段。

**断言的实现方式（谁持有上一次的值）**：应用维护一张内存表 `Map<"${id}\u0000${group}", { stability, hash, threadId }>`，每次组装时比对。**表不持久化**——重开应用后的第一次请求不比对（没有基准），从第二次请求起生效。不一致时：开发期控制台报警，运行时写入一条可查询的诊断队列并在成本面板显示为「缓存失效」来源。**不做持久化是刻意的**：这张表的用途是"发现我们自己的前缀抖动"，跨进程重启比对没有意义。

学习模块的「全册骨架」= 一个 `volume` 段（`group` = `documentId`），「当前章全文」= 一个 `chapter` 段（`04` §2.1）。

### 2.6 `prompts` —— 系统提示词、人格与技能

```ts
type PromptContribution =
  | { kind: 'system'; id: string; order: number; text: string }         // 系统提示词片段
  | { kind: 'persona'; id: string; name: string; text: string }         // 人格（由 Profile 选用）
  | {
      /** 可执行的"能力"：由插件贡献一条可被用户触发的任务（v1 的学习技能就是它） */
      kind: 'capability'
      id: string
      order: number
      label: string                  // UI 上的按钮名
      /** **开放字符串**，由插件定义取值与语义（v1 学习模块用 'selection' | 'chapter' | 'volume'） */
      scope: string
      instruction: string            // 本轮任务指令
      /** 两阶段能力的第二轮指令（04 §4.1） */
      followUpInstruction?: string
    }
```

**为什么 `kind: 'capability'` 用开放字符串而不是 `StudySkill`**：与 `Thread.scope` 同一个道理（`02` §2.3）——核心不得引用插件类型，否则 `packages/plugin` 就依赖了 `plugins/study`，删掉 `plugins/` 后编译失败（不变量 4）。`04` §4.1 的 `StudySkill` 是**插件侧**的类型，它把这些字段交给核心，`scope` 的取值由插件自己定义与解释。

**v1 不实现 `kind: 'command'`（斜杠命令）**——它没有消费者（`04` 的 13 项技能都走 `capability`），而本项目的纪律是「没有消费者的贡献点不实现」（§9）。需要时再加。

**职责分层纪律**（见 `04` §4.4）：系统提示词放「角色与红线」，技能指令放「这一轮做什么」，两者不得重复同一条规则——同一条规则有两个真相源会让模型对它的注意力下降。

### 2.7 `providers` —— 能力提供者

```ts
type LlmProtocol = 'openai-chat-completions' | 'anthropic-messages' | 'google-native'

type ProviderContribution =
  | { kind: 'llm'; id: string; protocol: LlmProtocol; adapter: LlmAdapter }
  | { kind: 'content'; id: string; source: ContentSource }   // 额外内容源，见 §6

type LlmAdapter = {
  /** 唯一必需方法。duck typing：无基类、无继承、无装饰器 */
  stream(req: LlmRequest, signal: AbortSignal): AsyncIterable<LlmStreamEvent>
}

type LlmRequest = {
  model: string
  system: string
  /** 按稳定顺序拼好的消息（前缀在前） */
  messages: { role: 'user' | 'assistant' | 'tool'; content: string; toolCallId?: string }[]
  tools?: ToolContribution[]
  maxOutputTokens?: number
  /** 原样透传给请求体的额外旋钮（来自 ModelCapabilities.options） */
  options?: Record<string, unknown>
  /** 前缀分段：①②③ 与 ④⑤ 的边界。**适配器据此决定在哪打缓存标记**（04 §5.1.1） */
  segments: { id: string; stability: ContextSegment['stability']; text: string }[]
  cacheBoundaryIndex: number
}

type LlmStreamEvent =
  | { kind: 'text'; delta: string }
  | { kind: 'reasoning'; delta: string }
  | { kind: 'tool-call'; id: string; name: string; argsDelta: string }
  | { kind: 'usage'; usage: Usage }
  | { kind: 'done'; finishReason: 'stop' | 'tool-calls' | 'length' | 'error' }
```

**`cacheBoundaryIndex` 是必需的，不是可选的**：三家协议对前缀缓存的处理完全不同——`anthropic-messages` **必须显式**在最后一个前缀块上打 `cache_control: { type: 'ephemeral' }`，不打标记就完全不缓存；`google-native` 需要显式创建 `cachedContent`；`openai-chat-completions` 多数实现自动。**没有这个信息，`04` §2 的缓存经济账在 Anthropic 协议上永远不会生效，而指纹却显示"一致"，造成"看起来没问题"的假象。**

## 3. 能力端口

**端口 = 核心包访问外界的唯一途径。** 接口定义在这里，**实现由壳提供**。核心包（阅读器、Agent 运行时）不知道自己跑在 Tauri、浏览器还是 Android 里。

```ts
type Ports = {
  fs:     FsPort
  net:    NetPort
  secret: SecretPort
  store:  StorePort
  notify: NotifyPort
}
```

```ts
type FsPort = {
  readText(path: string): Promise<string>
  /** 原子写：实现必须先写临时文件再 rename，避免半截文件 */
  writeText(path: string, data: string): Promise<void>
  exists(path: string): Promise<boolean>
  listDir(path: string): Promise<{ name: string; isDir: boolean; size: number }[]>
  /** recursive 语义明确：父目录不存在时一并创建 */
  mkdir(path: string, opts?: { recursive?: boolean }): Promise<void>
  remove(path: string, opts?: { recursive?: boolean }): Promise<void>
}
// 路径语义：应用数据目录内的相对路径；唯一例外是用户在设置里显式指定的内容目录
// 错误：一律 reject 一个带 code 字段的错误（'not-found' | 'denied' | 'io'）

type NetPort = {
  fetch(req: {
    url: string
    method?: 'GET' | 'POST'
    headers?: Record<string, string>
    body?: string
    signal?: AbortSignal
    timeoutMs?: number
  }): Promise<{
    ok: boolean
    status: number
    statusText: string
    headers: Record<string, string>
    body: ReadableStream<Uint8Array> | null
  }>
}
// 取消语义：signal.abort() 与 body.cancel() 等价，两者都必须中断底层请求

type SecretPort = {
  /** 键不存在返回 undefined；库未解锁时 reject 一个 code: 'locked' 的错误 */
  get(key: string): Promise<string | undefined>
  set(key: string, value: string): Promise<void>
  delete(key: string): Promise<void>
}

type StorePort = {
  get(table: string, key: string): Promise<unknown | undefined>
  put(table: string, key: string, value: unknown): Promise<void>
  delete(table: string, key: string): Promise<void>
  getAll(table: string): Promise<unknown[]>
  /** 按索引查询（不是全表过滤）。表与索引定义见 02 §4 */
  query(table: string, opts: { index?: string; range?: IDBKeyRange; limit?: number }): Promise<unknown[]>
}

type NotifyPort = {
  notify(title: string, body: string): void
}
```

### 3.1 三种形态的实现

| 端口 | PC（Tauri） | 静态网页 | 安卓（后续 Capacitor） |
|---|---|---|---|
| `FsPort` | Tauri `fs` 插件 | **空实现**（内容改走 `NetPort`） | Capacitor Filesystem |
| `NetPort` | Tauri `http` 插件（请求从 Rust 侧发出，**不受 WebView CORS 限制**） | 浏览器 `fetch` | Capacitor HTTP |
| `SecretPort` | Tauri `stronghold` | **空实现**（无 AI） | 系统安全存储 |
| `StorePort` | IndexedDB | IndexedDB（**两个实例**，见下） | IndexedDB |
| `NotifyPort` | 系统通知 | `Notification` API | 本地通知 |

**「静态版阉割 AI 与记录」是换掉 2 个端口 + 改一处装配，不是删代码分支**：

| 项 | PC | 静态 |
|---|---|---|
| `FsPort` / `SecretPort` | 有实现 | → 空实现（**2 个端口**） |
| `StorePort` | 1 个实例（IndexedDB） | **2 个实例**：`store` = IndexedDB（**只放内容缓存**，让已读的册离线可用）；`ephemeral` = 内存实现（放会话 / 进度 / 书签）→ 关掉即无记录 |

阅读功能一行不动，也就不存在「PC 版修好了静态版没同步」的漂移。这是本架构最有价值的一条性质。

**`NotifyPort` 在 v1 没有消费者**（没有后台任务、没有无人值守场景）。按「没有消费者的贡献点不实现」的纪律，**接口保留、实现推迟**到真有场景时。

### 3.2 平台机制的两个必须知道的事实（否则设计落不了地）

| 机制 | 事实 | 应对 |
|---|---|---|
| **Tauri `fs` scope 是静态声明，但可运行期扩展，且扩展只能从 Rust 侧做** | `app.fs_scope().allow_directory(path, true)` **没有对应的 JS API** | 「用户在设置里选一个内容目录」这条需求必须落成**壳在 `setup` 里的一小段 Rust**：读配置 → `allow_directory`。这不算业务逻辑，是**权限映射**，不违反 `00` §2.2 的「壳零业务逻辑」。同时 `01` §3 的 `FsPort` 需要 `fs:allow-mkdir` 等**非默认**权限（Tauri 2 默认只给 app 目录的递归**读**，递归写不是默认） |
| **Tauri `http` 插件默认不允许任何 origin** | 用户自填端点（含 `http://127.0.0.1:8045`）无法预先枚举 | capability 里对 `http://**` 与 `https://**` 开 scope。这是「用户自填端点」的**必然代价**，如实记录，不假装能收窄 |

**`stronghold` 的密码流程**（原文档缺失，必须定案）：首次运行时应用**随机生成 32 字节口令**，存入 **Windows 凭据管理器**（不是配置文件）；stronghold 用 `argon2` 派生密钥解锁。用户**永远不需要看见也不需要输入**这个口令——这样「零配置可用」与「密钥永不出现明文」同时成立。

## 4. 生命周期与可逆注册

| 动作 | 行为 |
|---|---|
| 加载插件 | 读 `manifest` → 按 `activation` 决定时机 → 动态 import → `await setup(ctx)` → 收集其全部注册返回的注销函数 |
| 卸载插件 | **逆序**调用全部注销函数 → 工具 / 视图 / 插槽 / 上下文提供者 / 提示词全部消失，不留残渣 |
| 卸载后 | 历史会话仍可读；该插件的工具不可再被调用（返回 `kind:'error'`，不崩） |

**契约纪律**：插件**不得在 `setup` 之外持有全局可变状态**；所有资源获取必须走 `ctx`，否则内核无法回收。这是「可精简」成立的技术前提，不是风格建议。

### 4.1 失败路径（v1 缺失，必须定义）

| 情况 | 行为 |
|---|---|
| **`setup` 抛异常**（`onStart` 插件） | 该插件标记失效、**回滚它已注册的全部项**、记一条错误日志，**其余插件继续、应用照常启动**。不中断启动——一个插件坏掉不该让整个应用打不开 |
| **`setup` 抛异常**（`onView`/`onDemand` 插件） | 同上，另外该视图显示一个可读的失败提示（不是白屏） |
| **异步 `setup` 未完成** | `onStart` 插件必须 await 完成后才渲染视图宿主（§1.2）；`onView`/`onDemand` 插件加载期间视图显示加载态 |
| **`ToolContribution.execute` 抛异常** | 转成 `ToolResultItem { ok: false, text: <异常摘要> }` 交给模型，**与 `kind:'error'` 走同一条路**；不终止整个 turn。原始异常同时写入本地日志 |
| **插件的 React 组件抛异常** | 每个插槽容器包一层错误边界：该插槽渲染为 `null` 并记日志，**不影响阅读器其余部分** |
| **`ContextContribution.provide` 抛异常** | 跳过该段（记日志），其余段正常组装。**不因为一个插件取不到上下文就让整轮失败** |

## 5. 装配三层与配置合并

### 5.1 三层

| 层 | 形态 | 举例 |
|---|---|---|
| **Base** | `packages/app` 里的**常量表** | 内置视图、基础端口、默认配置 |
| **Profile** | 同上常量表里的**具名组合** | `reader`（只装阅读）、`full`（装全部）。**Profile 同时决定 agent 人格与可用工具集** |
| **User** | 用户配置里的覆盖 | 启停插件、改参数、加自定义模型 |

**Profile 是代码里的常量表，不是用户可写的配置**：`AppConfig.profile` 只存**键名**（如 `"full"`），「键名 → 组合」的映射表住在 `packages/app`，启动时解析。这样用户不能通过改配置造出无法构建的组合。

### 5.2 合并策略（明确到不留歧义）

- **深合并的对象是三层各自的 `{ plugins, reader, ... }` 片段**，后者胜
- **插件装配用以插件 id 为键的对象，不用数组**：

```ts
plugins: {
  'study': { enabled: true, settings: { ... } },
  'some-experiment': { enabled: false },
}
```

**为什么不用数组**：数组拼接会导致「要禁用一个 Base 插件就得重述整个列表」；数组替换又会让 Profile 无法增量。对象以 id 为键时，深合并天然支持「只写要改的那一项」。

- **不发明 patch 语言**（不用 `!!js` 表达式、不做按 id 定位的补丁条目）。单人项目里，对象深合并 + 一个 `enabled` 开关已经够用（保留《原纲》判断）。
- 配置**不含任何密钥**，密钥只走 `SecretPort`。

## 6. `ContentSource`（内容源接缝）

接口定义见 `03` §2.1。这里是它在插件体系里的位置——**v1 的归属曾经写错，这里定案**：

| 项 | 归属 |
|---|---|
| `GitHubSource` / `LocalDirSource` **两个实现** | **内置模块 = `packages/app`**（装配层）。**不在 `plugins/` 下**——否则删掉 `plugins/` 后阅读器就没有内容源，不变量 4/5 同时失败 |
| `ContentSource` **接口定义** | `packages/reader`（阅读器只认接口） |
| `providers` 贡献点的 `kind: 'content'` | 用于**额外**内容源（如企业内部文档）。v1 无消费者，**不实现**，只保留类型位 |

「内置模块」在本文档中一律指 **`packages/app`**——即壳层里与业务无关的装配代码（视图宿主、插槽宿主、端口装配、内容源装配）。

## 7. 验收标准

| # | 标准 |
|---|---|
| 1 | **删掉整个 `plugins/`，项目仍能构建并启动**为可对话的空 agent、且阅读器完整可用（不变量 4/5） |
| 2 | 写一个 hello-world 级插件，验证：注册 → 界面出现 → 卸载 → 界面干净、无残留 |
| 3 | 在 `setup` 里只注册不注销（故意违反契约）时，卸载后能观察到残留 → 证明可逆注册是被真正执行的 |
| 4 | **故意让一个 `onStart` 插件的 `setup` 抛异常**：应用仍能启动、其余插件正常、坏插件的注册项无残留 |
| 5 | **故意让一个插槽组件抛异常**：只有该插槽变空，阅读器其余部分正常 |
| 6 | 六个贡献点各有至少一个真实消费者（**没有消费者的贡献点不实现**，见 §9） |
| 7 | `stability` 断言能捕获一次故意的缓存破坏（如往 `volume` 段里塞时间戳），并在成本面板可归因 |
| 8 | 换掉 2 个端口 + 换 `StorePort` 装配即得到可用的静态版，且关闭重开后无任何记录残留 |
| 9 | `LlmRequest.cacheBoundaryIndex` 在 `anthropic-messages` 适配器上确实产生了 `cache_control` 标记（用抓包或日志验证） |
| 10 | 工具重名、注册未声明的贡献点：前者报错、后者警告（已定义的严格度边界） |
| 11 | `pnpm verify:boundaries` 通过（见 §8） |

## 8. 边界校验脚本（不是 CI）

不变量 3/4/5 都要靠它验收，但**不引入 CI 复杂度**（`00` §10 R10）。定案：**一个本地脚本 `pnpm verify:boundaries`**，做三件事：

1. 解析 `packages/reader` 与 `apps/reader-web` 的 import，比对白名单（禁止出现 `packages/agent`、`plugins/*`、Tauri / Capacitor 包）
2. 临时移出 `plugins/` 后跑一次构建（不变量 4）
3. 对 `apps/reader-web` 产物做关键词扫描：`selectionchange` / `getSelection` / `apiKey` / `Bearer` / `chat/completions`（**不扫类型名**——TS 类型编译后已被擦除，扫它等于没验）

M1 的验收就是"跑这个脚本 + 人工读一遍一册"。

## 9. 实现顺序（防止为机制而机制）

**按真实消费者增量实现**，不一次做完六个贡献点：

| 阶段 | 实现 | 消费者 |
|---|---|---|
| **M1** | `views` / `slots` | 书架、阅读器、设置页的装配（全部来自内置模块） |
| **M2** | `context` / `tools` / `prompts` / `providers` | `plugins/study`：全册骨架注入、四个只读工具、系统提示词与技能、自定义模型适配器 |

**这条顺序是对 v1 的修正**：v1 把 `context`/`tools` 放在 M1，但它们的唯一消费者 `plugins/study` 是 M2 才存在的，而 M1 的验收又要求"删掉 `plugins/` 仍能完整阅读"——两者矛盾。现在 M1 只实现**内置模块自己就要用**的两个贡献点。

这是应对总纲 **R4**（插件机制空转）的具体手段：**每个贡献点在实现的那一刻就有一个真实消费者**。
