# 04 · 学习交互设计

> **文档性质**：模块设计。定义 AI 学习交互的会话模型、上下文组装、划词引用链路、学习技能与降级路径。
> **上位依据**：`00-架构总纲.md`、`03-阅读器设计.md`。`QuoteRef` 与数据表结构见 `02-数据模型.md`。
> **版本**：v1 · 2026-09-22
> **本文的地位**：AI 交互是**次要功能**。本文的一切设计都必须服从一条前提——**没有模型时，应用功能零损失。**

---

## 0. 定位与硬前提

### 0.1 三条硬前提

| 前提 | 含义 |
|---|---|
| **AI 可选，不是必备** | 未配置自定义模型时，入口**仍然可见但安静**；点进去是可行动的配置引导。**不显示灰按钮、不弹错误、不弹启动向导**；阅读功能零影响 |
| **只答注入的内容** | 模型只依据注入的当前章全文作答；章内没有的内容必须明确说「本章未涉及」，**禁止凭空脑补**（这是流水线一贯的红线） |
| **一切业务语义在插件里** | 学习技能、提示词、工具全部是 `plugins/study` 的产物，核心不含任何学习概念（总纲 §1.3） |

### 0.2 交互形态

文档为主 + **右侧对话栏（默认收起）**。划词后输入框自动带上引用卡片（显示「《册名》· 章名 · 节名」），直接打字即提问。

## 1. 会话模型

### 1.1 两类会话，各对应一个稳定前缀

| 会话 | 绑定 | 前缀区内容 | 用途 |
|---|---|---|---|
| **章会话**（主） | 一册 + 某一章 | 系统提示词 + 全册骨架 + **当前章全文** | 随阅读自动切换；划词提问落在这里 |
| **册会话**（辅） | 一册 | 系统提示词 + 全册骨架（**不含任何章全文**） | 「本册讲了什么」「第 3 章和第 7 章什么关系」 |

**一章一会话（线程）**：用户在整册里滚动到哪一章，右栏就切到哪一章的线程。翻回上一章，那一章的对话原样还在。

这样设计的原因是缓存与一致性：**换章是换线程，不是改写同一线程的前缀。** 改写前缀会让历史消息与上下文对不上，且缓存全废。

### 1.2 线程生命周期

| 事件 | 行为 |
|---|---|
| 进入某一章 | 按 `scope = { kind: 'chapter', key: '<documentId>#<chapterIndex>' }` 取线程；不存在则新建空线程（**空线程几乎零成本**） |
| 同一章内继续提问 | 追加到该线程历史 |
| 切换到另一章 | 挂起当前线程，切到目标章线程 |
| 关闭册 | 线程持久化（未配置存储时自然丢弃） |
| 内容改版导致章位移 | 线程的 `binding` 内含 `documentId` / `chapterIndex` / `chapterTitle`；打开该册时比对当前章标题，不一致则写 `staleAt` 并标注「内容已更新」，**不静默错位**（`02` §2.4） |

**注意这是插件的约定，不是核心规则**：核心只认 `Thread.scope: { kind, key }` 与不透明的 `binding`，从不解释它们的内容（`02` §2.3）。上面这些具体取值写在 `plugins/study` 里。所以第二个任务可以用自己的 `scope.kind` 与 `binding`，**不改核心一行**。

### 1.3 会话三原语（简化版）

沿用《原纲》从 Codex 借鉴的三原语，但**取消 wire 编码**（无跨进程传输，不再需要 JSON-RPC / SSE 编解码）：

| 原语 | 定义 |
|---|---|
| **Item** | 输入 / 输出原子单元：用户消息、助手消息、工具调用、附件。`started → delta* → completed` |
| **Turn** | 一次用户输入触发的一轮工作，聚合其产生的全部 Item |
| **Thread** | 可持久化会话容器，`scope` 由插件定义 |

数据定义见 `02-数据模型.md` §2（含 `MessageAttachment` 的不透明附件机制）。流式仍然有（模型输出逐字），只是它是**同进程内的 async iterator**，不是网络协议。

## 2. 上下文组装（本设计的核心）

### 2.1 三段式

```
┌────────────────────────────────────────┐
│ ① 系统提示词                            │  ← 全局稳定，跨线程、跨册共享
├────────────────────────────────────────┤
│ ② 全册骨架：册主旨 + 章标题 + 章元信息    │  ← 全册内逐字节稳定
│    （本册内容 / BLK 编号 / 覆盖分集）      │
├────────────────────────────────────────┤
│ ③ 当前章全文                            │  ← 章会话内稳定
╞════════════════════════════════════════╡  ← 缓存边界（prefix cache 命中依据）
│ ④ 会话历史                              │  ← 逐轮增长
├────────────────────────────────────────┤
│ ⑤ 划词引用（含章节路径）+ 本轮任务        │  ← 每轮变化
└────────────────────────────────────────┘
```

**所以 ② 必须按"两种批次各自固定一套字段"来序列化**（实测两套格式，见 `03` §1.2）：

| 批次 | ② 的构成（字段顺序固定） |
|---|---|
| 晚期 56 册 | 册主旨（`**本册内容**`）+ 每章：章标题 + `对应块` 编号 + `覆盖分集` + `块标题` |
| 早期 102 册 | 每章：章标题 + `对应分集` + `原始标题`（**没有册主旨、没有 BLK 编号**） |

**关键纪律**：同属一个批次的册，② 的字段集必须**完全一致、顺序一致**——不同批次之间可以不同（它们是不同的册、不同的前缀，缓存本来就各自算），但**同一册内不允许出现"有的章有 `块标题`、有的章没有"这种抖动**。缺失字段用固定占位（例如 `块标题：（无）`）而不是省略该行，这样字段数恒定。

**② 的来源全部在文档自身里**：册主旨取自册首元信息块，章标题取自 H2，章元信息取自章头引用块。不需要解析课程 README，也不需要任何外挂摘要。早期批次缺册主旨——**这是正常状态，不是解析失败**。

**这是「兼顾缓存命中率」的具体答案**：切章时 ①② 仍然命中，只失配 ③ 之后的部分；回到同一章完全命中；册会话连 ③ 都没有，前缀更短更稳定。

### 2.2 三条硬规则（继承并加强《原纲》§7.2）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **前缀区（①②③）不得含任何易变数据**——滚动位置、时间戳、未读状态、当前选中文本一律不进 | 易变数据会让缓存每轮全废，「全文注入」的经济账就不成立 |
| 2 | **划词永远作为新的 user 消息走消息层（⑤），绝不回写前缀** | 回写前缀 = 缓存全废 = 成本爆炸 |
| 3 | **全册骨架由确定性序列化生成，字段顺序固定** | 字段顺序抖动也会导致前缀不逐字节一致，缓存不命中 |

### 2.3 为什么章是注入单位（实测支撑）

真实文件层级：册 H1 → 章 H2（**原文逐字保留的一篇模块长文**）→ 节 H3 → 小节 H4。

**实测容量**（全库 1462 个 H2 段，2026-09）：中位 **10.6 KB**、p90 31.5 KB、最大 **75.8 KB**。按约 3.2 字节/token 折算：

| | 中位 | p90 | 最大 |
|---|---|---|---|
| **一章** | ~3.3k token | ~10k token | **~24k token** |
| **一整册** | — | — | 17.9 KB ~ 283 KB ≈ **5.6k ~ 88k token** |

（统一按 **3.2 字节/token** 折算；`04` §5.2.1 的预算估算用同一个系数。）

| 方案 | 成本 | 跨章推理 | 结论 |
|---|---|---|---|
| 注入整章 | 中位 ~3.3k，最大 ~24k token | 同章内完整；跨章靠工具 | **采用** |
| 注入整册 | 6k ~ 94k token | 最强 | 最大的册接近 94k，128k 窗口的模型叠加历史与输出就会溢出，成本也高一个量级 |
| 注入当前可见节 | 最小 | 差 | 破坏「这节和上节什么关系」这类最常问的问题 |

用户感知到在读一整册（显示单位），每次请求只付一章的上下文成本（注入单位）——**两者分离是本设计的核心。**

### 2.4 需要跨章时怎么办：交给工具

章会话的模型只能「看见」当前章，但**知道全册有哪些章**（②全册骨架）。需要别章内容时它自己调工具：

| 工具 | 作用 | 成本 | 实现 |
|---|---|---|---|
| `read_chapter(chapterIndex)` | 读**当前册**其他章全文 | 内存（当前册已解析） | `ContentQuery.getChapter` |
| `search_document(query)` | **当前册**内检索，返回命中片段与所在章 | 内存 | `ContentQuery.searchDocument` |
| `list_documents()` | 列出**本课程**全部册与笔记及其标题 | **缓存或网络**（跨文档，不在当前册内存里） | `ContentQuery.listDocuments` |
| `read_notes(topic?)` | 读**本课程**的复习笔记 | **缓存或网络**（是另一批文件，115 篇） | `ContentQuery.getDocument` |

**册由 `exec.thread` 提供，不进工具入参**：模型不知道也不该知道"用户正在读哪一册"。`ToolExec`（`01` §2.4）里有 `thread`，插件从 `thread.binding.documentId` 取当前册。`list_documents` / `read_notes` 同理从 `thread.binding.courseId` 取课程。

**成本分档的纪律**：上表后两项**会走 `ContentQuery` → `ContentSource` → 可能触发网络**，因此不能声称"零网络"。它们命中缓存时是快的，首次调用要拉取——这是正常的，但必须在提示词与 UI 上让用户知道（工具执行期间显示"正在读取…"），不能假装瞬时。

**四个工具都由 `plugins/study` 注册**（贡献点 `tools`），实现在**同一进程内**，不需要独立服务进程。阅读器只暴露 `ReaderApi`（导航）与 `ContentQuery`（内容）两个只读接口给插件；阅读器本身**不知道 agent、工具、模型是什么**（守住 `03` §0.1 的边界）。

## 3. 划词引用的完整链路

### 3.1 从选区到请求

```
① 用户划选一段文字
     ↓
② 学习插件用浏览器 Selection API 找到最近的 [data-block-id] 容器
     ↓
③ 用阅读器的 getBlockContext(blockId) 拿到章序号与标题路径（03 §9.4）
     ↓
④ 组装 QuoteRef：{ courseId, documentId, chapterIndex, chapterTitle,
                    sectionPath: ["章","节","小节"], blockId, text }
     ↓
⑤ 作为本轮 user 消息的结构化附件进入 ⑤ 区（消息层）
     ↓
⑥ 模型看到的语义：
   「用户正在阅读《课程名》的《册名》整册，当前在第 N 章《章名》。
     正在引用这一节（路径）的内容：
     > …原文…
     任务：<技能或自由输入>」
```

**整条链路的代码都在 `plugins/study` 里**，阅读器只被调用（`getBlockContext` / `scrollToBlock`）。所以静态版不装载这个插件时，链路上每一环都不存在——不需要任何 `if (aiEnabled)` 判断。

### 3.2 引用卡片

UI 上渲染成引用卡片，显示**出处**（《册名》· 章名 · 节名），可点击滚动回原文位置（用 `blockId` 在本次会话内定位；跨会话则用章节路径定位，见 `03` §9.1）。

### 3.3 引用可叠加与可移除

- 一次提问可带**多个引用**（比如「这两段矛盾吗」）
- 引用卡片可单独移除
- 引用原文**随消息存文本**，不存块 id → 文档改版后历史对话依然可读

## 4. 学习技能

### 4.1 技能是数据，不是代码分支

一条技能 = 一行配置：

```ts
/** 插件侧类型。字段与 01 §2.6 的核心 kind:'capability' 一一对应（label/scope/instruction/...） */
type StudySkill = {
  id: string
  label: string                       // UI 上的按钮名（= 核心的 label）
  scope: 'selection' | 'chapter' | 'volume'   // 插件自己定义的取值域
  instruction: string                 // 注入到 ⑤ 区的任务指令
  /** 两阶段技能的第二轮指令（如"生成自测题"：第一轮只出题，用户作答后换这条） */
  followUpInstruction?: string
  order: number
}
```

**注册通道**：技能表由 `plugins/study` 通过贡献点 `prompts` 注册，kind 为 `'capability'`（`01` §2.6）。**新增技能 = 加一行**，不需要改核心、不需要改阅读器。出现未知技能不影响任何既有功能。

**注意核心不引用 `StudySkill`**：`01` §2.6 的 `kind: 'capability'` 用中性的 `label` / `scope: string` / `instruction` 字段承载，`scope` 的取值（`'selection'` / `'chapter'` / `'volume'`）由本插件定义与解释。下表的 `StudySkill` 是**插件侧**类型，它把这些字段交给核心（与 `QuoteRef` 同理）。

**两阶段技能的机制**：`followUpInstruction` 存在时，技能的第一轮用 `instruction`，同一线程的**下一轮**改用 `followUpInstruction`（替换而非叠加）。这是「先给题、后给答案」与「费曼复述检查」能成立的前提——否则用户作答那一轮模型看到的仍是"先只给题"，会重复出题。

### 4.2 划词技能（`scope: 'selection'`，**9 项**）

> 全库技能总数是 **13 项**：本节 9 项划词技能 + §4.3 的 4 项章 / 册技能。文档别处提到"9 项"时指的是划词这一组。

| # | 技能 | 指令职责（要做什么，不是最终提示词） |
|---|---|---|
| 1 | **解释这段** | 用更朴素的语言重讲，**保留专业术语**（术语换掉就失去了检索价值） |
| 2 | **举个例子** | 给一个具体、可验证的例子；抽象概念优先给类比，并说明类比的边界在哪 |
| 3 | **补全推导** | 把文档为了流畅而省略的中间步骤补出来（对公式、证明、算法尤其重要） |
| 4 | **反问我** | 反过来考用户：这段的结论依赖哪些前提？换掉某个条件会怎样？**每次只问一到两个问题，等回答** |
| 5 | **和前后文的关系** | 这段与上一节 / 下一章是什么关系；若需要别章内容则调用 `read_chapter` |
| 6 | **考点与易错点** | 这里通常考什么、最容易错在哪、和哪个概念最容易混（文档本身有「易错点」标注时可引用它） |
| 7 | **生成自测题** | 3~5 道，覆盖本段；**先只给题，等用户作答后再给答案与解析**（这是关键：不能直接给答案） |
| 8 | **生成记忆卡** | 问答对形式，可就地复习翻面。**不导出**（与「不做摘录本」一致） |
| 9 | **检查我的复述** | 用户自己复述，模型指出遗漏、错误与不准确之处。**必须先肯定对的部分再指出问题**，否则人不会再用第二次 |

### 4.3 章 / 册级技能（`scope: 'chapter' \| 'volume'`）

| 技能 | 粒度 | 说明 |
|---|---|---|
| 本章讲了什么 | 章 | 结构化摘要，含与全册其他章的衔接 |
| 我没读懂 | 章 | 给出三个**更小的切入点**，让用户选一个继续（而不是把整章再讲一遍） |
| 本册知识地图 | 册 | 基于全册骨架给出章与章的关系（册会话） |
| 跨章对比 | 册 | 「第 N 章和第 M 章什么关系」→ 用 `read_chapter` 取内容（册会话） |

### 4.4 提示词的职责分层（不许混）

| 层 | 归属 | 内容 |
|---|---|---|
| 系统提示词（①） | `plugins/study` 的 `prompts` 贡献点 | 角色与红线：只依据注入内容作答；引用要标出处；章内没有就明说；不编造公式与代码；中文作答 |
| 全册骨架 + 章全文（②③） | `context` 贡献点 | 纯内容，不含任何指令 |
| 技能指令（⑤） | 技能表 | 只描述「这一轮要做什么」 |
| 引用载荷（⑤） | **`plugins/study`** 从本轮 `MessageAttachment` 里解析出的 `QuoteRef` | 纯内容 + 出处（核心不认这个类型，只存不透明附件，`02` §2.1） |

**红线**：技能指令里**不得重复**系统提示词已经说过的红线（重复会让模型对红线的注意力下降，也导致同一规则有两个真相源）。

## 5. 自定义模型接入

### 5.1 只有一种模型形态

应用**不内置任何厂商、不做账号、不做额度、不托管密钥**。用户自己新建一条「自定义模型」：

```
显示名 / 端点地址 / 密钥 / 模型名 / 协议（三选一）/ 能力声明
协议：openai-chat-completions | anthropic-messages | google-native
```

本地的 `127.0.0.1:8045`、Ollama、任何中转站，都只是「一条自定义模型」。三个适配器都是纯 fetch + SSE，零 SDK 依赖。密钥走 `SecretPort`（见 `01-插件与端口契约.md`）。

### 5.1.1 缓存边界必须传给适配器（否则 §2 的经济账不成立）

三家协议对前缀缓存的处理**完全不同**，这是本节最重要的一条：

| 协议 | 缓存怎么生效 | 适配器必须做什么 |
|---|---|---|
| `openai-chat-completions` | 多数实现**自动**做前缀缓存 | 无需请求侧声明，但**必须按稳定顺序拼消息**（前缀在前） |
| `anthropic-messages` | **必须显式**在最后一个前缀块上打 `cache_control: { type: 'ephemeral' }` | **不打标记就完全不缓存**——这是最容易静默失效的一处 |
| `google-native` | 需要显式创建 `cachedContent` 并引用 | 要么先建缓存再引用，要么接受不缓存（v1 可接受，但要如实记录） |

因此 `LlmAdapter.stream(req, signal)` 的 `req` 里**必须带前缀分段信息**（`01` §2.7 的 `LlmRequest.segments` + `cacheBoundaryIndex`），适配器据此决定在哪切、往哪打标记。**没有这个信息，Anthropic 协议上"前缀稳定 → 缓存命中"永远不会发生，而 `segmentFingerprints` 会显示"指纹一致"——造成"看起来没问题"的假象。**

> 这条也解释了为什么 `Usage.cachedPrefixTokens` 必须允许"未知"（§6.2）：供应商不打标记时不缓存，但指纹仍一致，两者必须分开呈现。

### 5.2 能力声明

每条自定义模型附一份能力声明（**用户可改**，因为中转站的实际能力常与宣称不符）：

```ts
type ModelCapabilities = {
  contextWindow: number
  maxOutputTokens?: number
  supportsToolCalls: boolean
  supportsStreaming: boolean
  supportsReasoning?: boolean
  /** 原样透传给请求体的额外旋钮（如 reasoning_effort / thinking） */
  options?: Record<string, unknown>
}
```

`options` 这一项是必需的，不是可选装饰：中转站经常需要 `reasoning_effort` / `thinking` 之类的开关才能正常工作，而这类字段**无法穷举**。适配器把它按协议映射进请求体，应用本身不理解它。

**能力声明决定三件事**：

1. **上下文预算**：`contextWindow` 用于判断"前缀是否塞得下"（见下）
2. **功能可见性**：不支持工具调用时，**隐藏需要跨章工具的技能**（跨章对比、本册知识地图）——**采用"不暴露"而不是"降级为把相关章一并注入"**。理由：后者要么退化成把整册塞进上下文（正是 §2.3 否掉的方案），要么需要一个不可判定的"相关章由谁判定"。不暴露是可实现且可验收的。
3. **UI 提示**：不支持流式时不显示逐字输出效果（改为一次性出现），不支持 reasoning 时不显示思维链折叠

### 5.2.1 上下文预算与超窗口降级（不能只靠事后 usage）

**问题**：技术栈里没有分词器（`00` §3），三家协议的分词口径又不同，而 `Usage.prefixTokens` 是**事后**从响应里拿的，不能用于事前决策。本地 8k / 32k 窗口的模型很常见，"配了小模型反而不能问"是最尖锐的失败态。

**估算口径**（写死，不做多套）：按 UTF-8 字节数折算，中文约 **3.2 字节/token**，拉丁文本约 **4 字节/token**；两者按字符类别分别累加后求和。这是估算，**误差可接受**——因为它只用于决定"塞不塞得下"，不用于计费。

**降级规则**（必须实现，按顺序尝试）：

| 顺序 | 动作 | 何时触发 |
|---|---|---|
| 1 | 正常注入 ①+②+③ | 估算前缀 ≤ `contextWindow − maxOutputTokens − 历史预留` |
| 2 | 丢弃 ③（当前章全文），只留 ①+② | 上一步塞不下 |
| 3 | 把 ③ 换成"当前可见节"（H3 粒度） | 第 2 步导致无法回答章内问题、且仍塞不下时（罕见） |
| 4 | 拒绝并给出可行动提示 | 连 ①+② 都塞不下（窗口 < ~2k）：提示"当前模型的上下文窗口过小，无法承载整册骨架，建议换一个窗口 ≥ 8k 的模型" |

**第 4 步必须是一个明确的、带建议的提示**，而不是静默失败或抛异常——这是"未配置模型可读、配了小模型却不能用"的唯一体面出路。

### 5.3 界面状态机（右栏收起 / 展开与划词的交互）

「右栏默认收起」与「划词后输入框自动带上引用卡片」看似冲突——收起时输入框不可见。用一张状态机表定死（这决定 M2 一半的 UI 逻辑）：

| 事件 | 右栏 | 动作条 / 引用卡片 | 说明 |
|---|---|---|---|
| 打开一册 | **收起** | 无 | 阅读优先 |
| 划选一段文字 | **保持收起** | 选区旁浮起**动作条**（「复制引用」+「AI 讲解」） | 划词**不**自动展开右栏——否则每选一次字就被打断阅读 |
| 点「复制引用」 | 保持收起 | 动作条消失，提示"已复制" | 全程不打扰阅读 |
| 点「AI 讲解」→ 已配置模型 | **展开** | 动作条消失；**9 项技能列表渲染在右栏**；引用卡片进入右栏输入框 | 展开是用户主动发起的 |
| 点「AI 讲解」→ 未配置模型 | **展开** | 右栏显示**配置引导**（表单 + 「以后再说」） | 不是灰按钮、不是错误提示 |
| 手动点折叠条入口 | 展开/收起切换 | — | 展开时显示当前章的会话线程 |
| 点「以后再说」 | **收起** | 无 | 尊重用户的"不" |
| 滚动跨章 | 保持当前状态 | — | **右栏自动切到新章的线程**（`§1.1`）；切章不改变展开状态 |

**技能列表的位置**：在右栏，不在动作条上。动作条永远只有两项——把 13 项技能堆在选区旁会遮住正文。

### 5.4 模型调用失败路径（必须有定义，不能只留一个 `failed` 枚举）

这是日常最高频的四种情况，`02` 只给了 `ItemStatus` 枚举，行为未定。定案如下：

| 情况 | 部分输出 | 自动重试 | UI | 数据 |
|---|---|---|---|---|
| 端点连不上 / DNS / 超时 | 保留已流出的文本 | **不重试** | 错误就地显示在该条消息下方，附「重试」按钮 | `AssistantMessageItem.error = { kind: 'network' }`，`Turn.status = 'failed'` |
| HTTP 4xx（401 密钥错 / 404 模型名错 / 400 参数错） | 无（请求未成功） | **不重试** | 错误提示**必须带上状态码与响应体摘要**（用户自填端点，这是唯一能自助排查的信息） | `error.kind = 'http'`，附 `status` 与截断后的 body |
| HTTP 429 / 5xx | 保留已流出文本 | **不自动重试**（v1）；「重试」按钮可用 | 提示"上游限流或故障，稍后重试" | `error.kind = 'http'` |
| 用户点「停止」 | **保留已流出的文本**（这是用户的资产） | — | 消息标注"已停止" | `error.kind = 'aborted'`，`Turn.status = 'aborted'` |

**三条纪律**：

1. **已流出的文本永不丢弃**——无论哪种失败，用户已经看到的内容必须留在会话里。
2. **不自动重试**。重发整段前缀是有成本的（尤其缓存未命中时），静默重试会让成本面板的数字变得无法解释。让用户决定。
3. **取消通道必须贯穿四处**：`AbortSignal` 要能中断 `LlmAdapter.stream`、`ToolContribution.execute`、`ContextContribution.provide`、`ContentQuery` 的取数（`01` §2、`03` §9.5 已把这四处都列为带 `signal` 的签名）。"停止"按钮必须在**任意阶段**都有效，包括工具执行中与等待首 token 时。

### 5.5 未配置模型时的降级路径

**以下整表适用于 PC 版（已装载学习插件）。** 静态网页版不装载学习插件，本节完全不适用——它没有会话、没有模型、没有划词，就是一个纯阅读站（`03` §11.1）。

| 位置 | 行为 |
|---|---|
| 右栏 | **默认收起**（阅读优先，不是隐藏功能）；折叠条上有一个安静的入口。展开且未配置模型时显示**配置引导**：一句话说明「本软件不提供模型服务，需要你自己填一个端点」+ 一个表单 + 「以后再说」 |
| 划词动作条 | 固定两项：**「复制引用」**（复制带出处的一段文本，任何情况下都可用）与**「AI 讲解」**。点「AI 讲解」：**已配置模型**时展开 `§4.2` 的 9 项技能列表；**未配置**时直接打开上面的配置引导。两种情况都**不是灰按钮、不是错误提示** |
| 设置页 | 有「自定义模型」入口，**没有推销文案、没有引导问卷、不主动弹窗** |
| 其它功能 | 阅读、书架、搜索、进度、书签**全部不受影响** |

**这条设计遵循的原则与 `03` §3 书架空状态是同一条**：空状态是**行动邀请**，不是错误页。我最初写的是「整体隐藏」，那是把「不要摆出坏掉的按钮」错误地实现成了「不要让人发现这个功能」——两者不是一回事，后者会让愿意自己配模型的用户永远找不到入口。

**并且自定义模型的存在本身消除了隐藏的理由**：不存在「没账号所以永远用不了」的死路，只有「去配一下」的下一步。这正是「不内置厂商」这个决定带来的好处——把一次性的配置成本，换掉了永久的功能缺口。

这条是「分母发的用户」场景的关键：别人拿到 exe，打开就是能读全部课程，**不会因为没配模型而看到一堆坏掉的东西**。

## 6. 成本与缓存命中采集

### 6.1 采集什么

每次请求记录：模型、协议、前缀 token 数、**缓存命中 token 数**、输出 token 数、首字延迟、总耗时、以及**前缀指纹**（①+②+③ 的哈希）。

### 6.2 为什么必须采集前缀指纹

「前缀稳定 → 缓存命中」是本设计的核心经济假设。指纹让我们能**实测验证**它，而不是相信它：

- 同一章连续两轮，指纹应完全相同 → 缓存应命中
- 换章后，指纹应只在 ③ 处变化 → ② 之前仍命中
- 若指纹意外变化（字段顺序抖动、混入易变数据），一眼可见

**M2 的验收标准之一就是「实测 prefix cache 命中率」**——这条假设若在实际供应商上不成立，整个成本模型要重新算（见 `00-架构总纲.md` 风险表）。

### 6.3 未报告缓存字段时怎么办（否则 M2 验收无法判定）

命中数只能来自供应商响应（OpenAI 的 `prompt_tokens_details.cached_tokens`、Anthropic 的 `cache_read_input_tokens`、Gemini 的 `cachedContentTokenCount`）。而本应用的目标端点正是「本地 `127.0.0.1:8045`、Ollama、任何中转站」——**这些端点普遍不返回 cache 明细，甚至不返回 usage**。

定案：

| 情况 | `Usage.cachedPrefixTokens` | 成本面板显示 |
|---|---|---|
| 供应商报告了缓存明细 | 实际数值 | 命中率 |
| 供应商报告了 usage 但没有缓存字段 | **`-1`（未知）** | 「未知」，**与 0 分开显示** |
| 供应商什么都没报告 | `prefixTokens` 与 `cachedPrefixTokens` 都记 `-1` | 「不可观测」 |

**M2 验收口径相应收窄**（原口径"实测命中率"在多数端点上不可判定）：

> 在**至少一个会报告缓存明细的端点**上测得 `cachedPrefixTokens > 0`；在不报告的端点上，只要求 `segmentFingerprints` 逐轮一致（证明我们的前缀确实稳定），**不要求命中率数字**。

这样"我们的前缀是稳定的"（我们能控制）与"供应商真的命中了"（我们不能控制）被分开验证——**后者不可控，不能当作验收门槛**。

### 6.4 展示

v1 只在设置页给一个朴素的成本面板（按模型 / 按册汇总），不做图表。**不采集、不上传任何数据到任何服务器。**

| # | 标准 | 怎么验 |
